# Rust 改写前的关键约束

本篇归纳源码对后续改写的约束，不制定最终 Rust API，不承诺二进制兼容，也不开始编码。源码基线和验证边界见 [调查入口](README.md)。

后续决定已记录于 [RasterKV 第一阶段与支持库选型](05-RasterKV第一阶段与支持库选型.md)：对象名为 RasterKV，第一阶段完整覆盖单层 FasterKv 功能与行为，采用独立文件格式，F2 等后置。下文保留初次调查时的设计议题，其中旧文件兼容问题已经确定，不再是待决项。

## 需要优先保留的语义

| 主题 | 源码事实与证据 | 对 Rust 改写的启示（建议） |
| --- | --- | --- |
| 立即完成与异步完成 | `cc/src/core/status.h:10` 定义 `Ok`、`Pending`、`NotFound` 及错误状态；`cc/src/core/async.h:98` 定义操作回调 | 不要把 `Pending` 当成失败，也不要直接把提交成功当成最终结果；先明确立即结果和延迟结果的所有权 |
| 上下文生命周期 | `cc/src/core/async.h:35` 描述栈上下文转堆；`DeepCopy` 已深拷贝时返回自身；`CallbackContext` 在回调结束决定是否释放 | 不能机械地把指针变成借用；挂起请求必须拥有存活至最终完成的数据，嵌套上下文和再次挂起也需要覆盖 |
| 线程与会话 | `cc/src/core/thread.h:24` 设定 96 个线程槽，`:79` 使用线程局部 ID；`cc/src/core/faster.h:696`、`:713`、`:766` 实现开始、恢复、结束会话 | 会话不是随意跨线程移动的普通值；如改为任务调度或异步运行时，应明确任务迁移、会话绑定和退出排空的语义 |
| 协作推进 | `cc/src/core/faster.h:733` 的 `Refresh` 推进 epoch 和特殊阶段；`:948` 的 `CompletePending` 轮询设备、索引、完成队列及重试队列 | 单独返回一个 Future 并不会自动推进原协议；需要明确由谁驱动 I/O、回调、重试和检查点阶段 |
| 返回值之外的错误 | `cc/src/core/faster.h:699` 在非 REST 阶段开始会话会抛异常；`:717` 在恢复未知会话时抛异常 | 错误契约不仅是 `Status` 枚举；转换为 Rust 错误类型时应覆盖异常和前置条件 |
| 逻辑地址编码 | `cc/src/core/address.h:24` 的无效地址为 1；`:30` 起使用 48 位地址、25 位页内偏移，最高地址位可标记读缓存 | 保留无效值与空索引项的区别；使用显式位运算和边界验证，不能把所有地址等同于裸文件偏移 |
| 记录布局 | `cc/src/core/record.h:14` 的 `RecordInfo` 为 8 字节，包含前驱地址、检查点版本、invalid、tombstone、final；`:88` 起按 Key/Value 对齐计算位置 | 持久化布局和 Rust 对象布局应分开考虑；`repr(C)` 本身不等于 C++ 位域或任意用户类型的磁盘兼容 |
| 可变长数据 | `cc/src/core/record.h:99` 根据实际 key 大小计算 value 位置；`:119` 起计算记录大小和磁盘最小读取长度 | Key/Value 不能简单限制为固定大小结构体而仍声称功能等价；需要明确编码、对齐、长度校验和缓冲区生命周期 |
| 原子发布 | `cc/src/index/hash_bucket.h:26` 的索引项打包为 8 字节；`:89` 起通过原子 load/store/CAS 更新 | 先保持原有发布和读取顺序，再考虑弱化内存序；不要只复制位布局而遗漏初始化与可见性约束 |
| 安全回收 | `cc/src/core/light_epoch.h:180`、`:204`、`:240` 分别涉及保护、解除保护和延迟动作 | Rust 所有权不会自动替代并发原始内存的回收协议；索引、日志页和异步读取之间的有效期仍需证明 |
| 检查点不是普通 flush | `cc/src/core/phase.h:26` 定义检查点、GC、扩容阶段；`cc/src/core/faster.h:3307`、`:3436` 实现 Checkpoint/Recover | 需要保留会话序号、版本、索引和日志之间的一致性语义；仅将所有页写盘不能视为等价恢复协议 |
| 平台后端 | `cc/src/environment/file.h:6` 选择 Windows 或 Linux 文件实现；`cc/CMakeLists.txt` 配置 Linux AIO 和可选 io_uring | 原代码没有独立 macOS 后端；本机能阅读源码不代表能直接构建或验证原实现 |
| F2 范围 | `cc/src/core/f2.h:20` 定义独立组合层；`:229` 起将同一会话标识用于热、冷存储；`:695` 起恢复两个存储 | F2 不是更换一个磁盘类型；若分阶段移植，需要明确阶段性未覆盖 F2，避免宣称完成全部 cc 功能 |

## 改写前应明确的范围

以下是后续设计需要作出的选择，本轮调查不要求立即决定：

1. **兼容目标**：行为兼容、性能特性接近，还是直接读取已有 C++ 日志与检查点。磁盘兼容应独立验证，不能由 API 相似推导。
2. **首个支持平台**：Linux 后端与 macOS 开发后端如何安排；是否同时支持 Windows、io_uring 和 Azure Blob。
3. **用户类型契约**：允许任意 Rust 类型，还是提供明确的编码/解码与变长记录接口；原代码中的原子读写回调责任如何表达。
4. **会话模型**：继续采用线程绑定和显式轮询，还是提供调度层；若提供 async API，需要保留明确的底层推进协议。
5. **功能覆盖顺序**：核心 KV、持久化恢复、压缩/扩容/读缓存、冷索引与 F2、可选云设备应分别记录完成状态。
