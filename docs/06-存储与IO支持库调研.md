# RasterKV 存储与 I/O 支持库调研

调查日期：2026-09-10。目标是完整复刻 C++ `FasterKv` 的功能，Rust 对外对象名为 `RasterKV`；F2、冷索引不在第一阶段。用户已确认第一阶段要求功能与行为一致，采用独立文件格式，无需读取 C++ 产生的文件。本文为依赖选型调查，不代表已引入依赖或验证性能。

## 1. 建议结论

**核心层保持不依赖 async runtime 的设备协议，先以标准库文件操作和有界工作队列建立可移植正确性基线，再接入 Linux `io-uring` 优化后端。** Unix 特殊文件选项优先使用 `rustix`，必要时小范围使用 `libc`；Windows 专用后端使用 `windows-sys`。对齐内存优先评估 `aligned-vec`，并在 RasterKV 内封装拥有缓冲和在途请求的生命周期。

`compio-driver` 是值得优先做小规模验证的跨平台完成式后端候选：它可以脱离 executor 手动驱动，减少直接维护 io_uring/IOCP 的代码。但它有线程归属、文件句柄附加和取消语义约束，不能在未验证前代替设备协议。`tokio-uring`、`monoio` 更适合用户明确选择相应 runtime 时的可选适配，不宜成为 RasterKV 核心的强制依赖。此段是结合下文官方事实作出的工程判断。

## 2. 原实现决定的约束

- `CompletePending(false)` 主动轮询完成、处理重试并推进会话；`CompletePending(true)` 持续推进直到挂起操作结束。它不是持久化提交。参见 [原 API 调查](03-功能与API契约.md) 和 [faster.h:948](https://github.com/microsoft/FASTER/blob/321d872eabda6a0345c8bd76419f89723ed864ae/cc/src/core/faster.h#L948)。
- 设备需要带偏移异步读写、返回实际字节数、对齐能力、完成轮询、分段管理和检查点文件操作。日志分段回收不能直接等同于某个文件的 `set_len`。参见 [file_system_disk.h:241](https://github.com/microsoft/FASTER/blob/321d872eabda6a0345c8bd76419f89723ed864ae/cc/src/device/file_system_disk.h#L241)。
- 会话有线程归属、协作 epoch 和检查点阶段。运行时完成一次文件读写，不会自动实现这些协议。参见 [迁移约束](04-Rust改写关键约束.md)。

## 4. 候选与适配成本

| 方案 | 已确认的能力与平台 | RasterKV 判断与边界 |
|---|---|---|
| `io-uring` | 暴露提交队列、完成队列、操作码及文件/缓冲注册，面向 Linux；无需绑定 executor。[官方文档](https://docs.rs/io-uring/0.7.15/io_uring/) | 最贴近手工 `CompletePending`；仅提供内核接口，需自管缓冲存活、短 I/O、请求 ID、取消、队列满及关闭排空。推荐 Linux 性能后端。 |
| `tokio-uring` | 要求 Linux 5.10+；内部 current-thread Tokio runtime；I/O 接收拥有缓冲并在完成时归还，多数资源 `!Sync`。[官方文档](https://docs.rs/tokio-uring/0.5.0/tokio_uring/) | 不能直接塞入任意已有 Tokio runtime；驱动必须被运行，紧循环 `CompletePending` 也不能饿死 executor。适合可选 async 门面；不覆盖 macOS/Windows。 |
| `monoio` | thread-per-core，Linux io_uring/epoll，macOS kqueue；文档将 Windows 视为尚未完成；线程本地任务不在 await 后跨线程迁移。[官方文档](https://docs.rs/monoio/0.2.4/monoio/) | 与线程会话较契合，但引入独立 runtime 和租借缓冲 I/O trait。不能把 kqueue 支持推导为普通文件拥有与 io_uring 相同的原生异步性能；需验证文件 fallback。 |
| `compio` | thread-per-core，后端 IOCP/io_uring/polling，使用拥有缓冲。[官方文档](https://docs.rs/compio/0.19.2/compio/) | 跨平台 async 候选；完整 runtime 并非必需。核心优先考虑下一行低层 driver。 |
| `compio-driver` | `Proactor` 拥有 operation，支持手工 `push`、`poll`、`pop`，自身 `!Send`/`!Sync`；IOCP 文件只能附加一个 driver，克隆也不消除此限制；取消不保证底层停止。[官方 API](https://docs.rs/compio-driver/0.12.5/compio_driver/struct.Proactor.html) | 可由专属设备线程驱动并回送会话完成队列，或明确按线程分配独立打开的句柄。不能简单每会话一个 driver 却共享同一文件句柄。应验证后再确定是否代替直接系统调用后端。 |
| `tokio::fs` | 所有平台当前使用 `spawn_blocking` 执行普通文件操作；写入后 `flush` 等待后台写完成。[官方文档](https://docs.rs/tokio/1.53.1/tokio/fs/) | 可作已有 Tokio 应用的兼容层，不是内核完成式文件 I/O。热点随机访问更适合有界工作队列中的定位读写；不应把共享 seek 游标当成并发定位 I/O。 |
| `rustix` / `libc` | `rustix::fs` 提供文件系统调用封装；`libc` 提供平台 C ABI。[rustix](https://docs.rs/rustix/1.1.4/rustix/fs/)、[libc](https://docs.rs/libc/0.2.189/libc/) | Unix 设备选项、同步、截断的薄层；优先有类型封装，缺口才用裸 FFI。两者都不会提供日志分段或完成调度器；按具体 API 设置平台 cfg。 |
| `windows-sys` | 微软维护的 Windows API 原始绑定。[官方仓库](https://github.com/microsoft/windows-rs) | 用于 IOCP/OVERLAPPED、无缓冲标志、同步与文件长度管理。必须自己处理句柄和在途结构生命周期；不是高级安全文件引擎。 |
| `memmap2` | 提供文件和匿名内存映射；文件映射涉及外部修改导致的不安全条件。[官方 MmapOptions](https://docs.rs/memmap2/0.9.11/memmap2/struct.MmapOptions.html) | 可评估匿名页分配或只读辅助数据，不作为 HybridLog 主设备的首选。用 mmap 替代原读写模型，会改变 page cache、缺页、截断和错误传播行为，不能称为直接复刻。 |

## 5. 对齐缓冲和持久化不能交给 runtime 隐式决定

`aligned-vec` 的 `AVec`/`ABox` 支持运行时对齐值，适合设备返回对齐要求后分配页面；`aligned-buffer` 提供独占可写缓冲和共享只读缓冲，适合特定共享读取场景。两者都只是内存容器，不能自动保证文件偏移、I/O 长度或写入持久化。[aligned-vec](https://docs.rs/aligned-vec/0.6.4/aligned_vec/)、[aligned-buffer](https://docs.rs/aligned-buffer/0.2.0/aligned_buffer/)

建议内部封装拥有缓冲：记录申请对齐、容量、已初始化长度和有效数据区间；提交后禁止扩容或修改，完成后才归还缓冲池。`compio-buf` 提供的是 `IoBuf`/`IoBufMut` 等安全契约，本轮未找到该版本提供专用对齐容器；实现其 unsafe trait 时仍需满足指针稳定与初始化规则。[compio-buf](https://docs.rs/compio-buf/0.8.3/compio_buf/)

Linux `O_DIRECT` 对地址、偏移、长度的限制依赖文件系统；Linux 6.1 起部分文件系统可通过 `statx` 的 `STATX_DIOALIGN` 查询。不能把 4096 写死为通用正确答案，且 direct I/O 不等于同步落盘。[Linux open(2)](https://www.man7.org/linux/man-pages/man2/open.2.html)

Windows 无缓冲文件读写要求扇区相关对齐，物理扇区与逻辑扇区可能不同；设备应单独报告内存和传输约束。[微软 File Buffering](https://learn.microsoft.com/en-us/windows/win32/fileio/file-buffering)

macOS 不走 Linux `O_DIRECT`/io_uring 路径。第一版可明确提供 buffered 定位 I/O 后端；若要做缓存绕过和更强刷盘语义，需单独验证 Darwin 设备选项，不可从 Unix 编译成功推导等价性。

`tokio-uring::fs::File` 提供 `sync_all`/`sync_data`；`compio-fs::File` 也提供同步方法，但当前文档将 `set_len` 标注为 Unix-only，旧 Linux 或未启用 io_uring 时可能走阻塞线程。不能仅凭 compio 支持 IOCP 就宣称 Windows 文件 API 全覆盖。[tokio-uring File](https://docs.rs/tokio-uring/0.5.0/tokio_uring/fs/struct.File.html)、[compio-fs File](https://docs.rs/compio-fs/0.12.1/compio_fs/struct.File.html)

因此 RasterKV 应分别表达：请求完成、数据同步、检查点提交完成、逻辑 begin 推进、物理段删除。检查点元数据写入、文件同步、目录项持久化及发布顺序由引擎制定；任何一个 crate 的 `flush` 都不构成整个检查点协议。此为设计建议，验收仍以原 FasterKv 功能契约和崩溃恢复测试为准。

## 6. 接入前最小验证项

1. 小文件定位读写：正常、短读、EOF、短写、错误返回，确认实际字节数与缓冲归还。
2. 同一会话线程主动推进：不启用外部 runtime 的 `CompletePending(false/true)`、检查点阶段推进以及关闭排空。
3. 对齐缓冲：真实设备约束、错误偏移/长度，以及错误后缓冲不会过早释放。
4. 分段截断与在途读取竞争、同步失败、检查点中断恢复；确认数据完成与持久化完成分开判定。
5. 至少在 Linux 与本机 macOS 验证基础后端；若选择 compio 或 Windows 后端，追加 IOCP 附加策略、取消排空和物理截断验证。
