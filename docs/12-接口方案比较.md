# RasterKV 接口方案比较

日期：2026-09-10。三名后台 agent 按不同约束分别设计，主 agent 综合。共同输入为完整 FasterKv 功能、独立文件格式、F2 后置、保留同步快速路径与异步完成能力。本文保存设计取舍，最终推荐以 [09](09-RasterKV模块设计.md) 和 [10](10-RasterKV公开接口.md) 为准。片段是对比示意，不是实现。

## 1. 方案 A：常用操作优先的类型化会话

```rust
session.read(serial, ReadValue::new(key), options) -> Submission<Value>;
session.rmw(serial, Increment::new(key, delta), options) -> Submission<u64>;
session.poll(budget) -> Result<Progress, SessionError>;
session.wait(&mut ticket, deadline) -> Result<OperationResult<T>, WaitError>;
```

调用例：提交两个读取，保存两张票据，再不断 poll，分别收取 String 和整数结果。内存命中时直接处理 Ready，不建立异步结果槽。

它把用户心智放在四种操作和一个线程会话上，隐藏页、索引、版本和磁盘继续执行。方法数较多，但与业务动作直接对应；类型系统避免异构结果手工转换。请求所有权转移解决 C++ DeepCopy，不过通用“拥有请求”也可能引入键复制，需要在实例化和便利方法中优化。

主要风险在等待/关闭：票据不能借用会话，否则等待期间无法 poll；会话 Drop 不能把非 Send 上下文发给后台。该方案最适合作为第一阶段用户接口。

## 2. 方案 B：少量入口的拥有型命令

```rust
session.submit(serial, Read::new(context)) -> Submission<ContextOutput>;
session.poll(mode) -> Result<Progress, SessionError>;
session.take(&mut ticket) -> Result<Completion<T>, TicketError>;
```

调用例：将同样的提交、推进和取出流程用于 ReadName、Increment、Delete 等不同上下文。用户实现读取/RMW 等安全协议，核心 Operation 是 sealed，禁止任意命令跳过索引和生命周期规则。

它的入口很少，能自然统一四种操作并保留复杂上下文。代价是所有调用者需要先学习命令包装、关联输出和操作 trait；减少方法数不必然减少调用者知识。若允许任意第三方 Operation 直接执行，反而把整个存储状态机暴露成公共协议。

该方案的深度来自内部统一执行，而不是一个万能公开 submit。推荐吸收它的拥有型任务、类型化输出槽和 sealed 内部调度，不让初学调用者必须先了解命令系统。

## 3. 方案 C：后台 actor 与 Future

```rust
let mut session = workers.start_session().await?;
let ticket = session.submit(serial, Upsert::new(key, value))?;
ticket.await?;
workers.checkpoint(CheckpointKind::Full)?.await?;
```

实际 Session 固定由后台工作线程持有，应用持有逻辑客户端。提交成功即接受，Future 只观察结果和登记唤醒；队列满归还命令。用户不再定期 Refresh，后台即使没有业务请求也推进维护阶段。

这一方案隐藏的进度管理最多，适合异步服务。它要求跨线程的命令和输出为 Send，使原来可以在线程中使用的非 Send 上下文受限；调用线程上的内存同步路径变成消息投递。多个 worker 可并发操作共享存储，但单个全局 actor 串行化全部操作不可接受。

Future 本身并不必然造成消息化：线程本地 Future 可以在 poll 内同步完成，但那是另一种带会话借用/本地执行约束的接口。本方案的便利性来自后台持有会话，必须承担队列和调度成本。丢 Future 只放弃结果，不撤销已经接受的写。

## 4. 综合选择

推荐采用 A 的四种公开方法，内部采用 B 的统一拥有型任务与类型化完成机制。用户最常见的读写可直接调用，复杂 RMW 仍有扩展空间；索引、日志和阶段管理集中在引擎，不从用户接口泄漏出去。

公开接口的复杂性主要来自必须保留的区分：请求被接受、请求已完成、检查点已持久化。三者不能为追求一个简单返回值而合并。Ticket 与 MaintenanceTicket 因语义不同保留独立类型，避免等待 I/O 被误认为检查点成功。

Schema/ValueLayout 是更重要的 Seam：同一操作应在通用同步值和专用原子值 Adapter 上运行。需要在这处集中解决安全视图与原地更新，而不是让四种操作分别操作裸日志内存。

C 保留为后续外观层，未来由 worker 真正拥有核心 Session 并推进，核心无需强制依赖 Tokio。不会为了将来的 Future 层给当前每个操作加 Send 或要求所有内存操作入队。

本轮不要求用户在三套方案中重新选择；09–11 已给出可以继续评审和实现的单一建议。若后续主要用例转为网络服务，可调整外观层，不必推翻日志、索引和恢复模块。
