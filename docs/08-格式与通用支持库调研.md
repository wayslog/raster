# RasterKV 格式与通用支持库调研

调查日期：2026-09-10。用户已确定：第一阶段完整复刻 FasterKv 的功能与行为，命名为 RasterKV，文件格式独立，F2 后置。本篇调查哈希、记录编码、元数据、配置、错误和观测支持库；I/O 与并发见 [06](06-存储与IO支持库调研.md)、[07](07-并发与验证支持库调研.md)。

## 1. 建议

优先候选为 `uuid`、`thiserror`、`serde`、`toml` 和 `zerocopy`；`tracing` 用于可选观测。`xxhash-rust` 是稳定哈希实现候选，`crc32c` 是独立格式校验候选。记录头、日志布局、提交协议及用户原子更新语义由 RasterKV 定义，不能由通用序列化框架代为决定。

`postcard` 可评估为非热点元数据或用户值适配器；`bytemuck` 是简单 POD 转换的备选，不必与 `zerocopy` 同时引入。`rkyv` 不作为可变日志记录的默认方案；`bincode` 不纳入新工程默认依赖。以下分别提供依据；采用判断是面向本项目的建议，未做性能比较。

## 3. 记录格式：优先显式布局与受约束转换

### zerocopy：推荐用于固定头与安全解析

`zerocopy` 提供 `FromBytes`、`TryFromBytes`、`IntoBytes`、`KnownLayout` 和字节序整数类型，支持对大小、对齐及部分位模式有效性进行约束。建议用于不含指针/内部可变性的磁盘头和元数据结构，启用 `derive`。带 Atomic 字段的活跃内存记录、可变长 Value 和用户逻辑有效性不能自动获得安全证明。[版本文档](https://docs.rs/zerocopy/0.8.57/zerocopy/)

项目需要自行检查 magic、格式版本、长度溢出、记录边界、状态位组合和校验值。即使某个头实现 `FromBytes`，也只代表其 Rust 位模式可接受，不表示它是合法 RasterKV 记录。读取磁盘数据时不要把 `Immutable` 视图与并发原子修改的内存对象混用。

### bytemuck：简单转换备选

它适合普通数据类型之间的转换，有 `try_` 接口，`Pod` 等 trait 带严格要求。官方文档说明无 feature 时支持 Rust 1.34，但 feature 可提高最低版本，因此表中不为 `derive` 组合虚构 MSRV。若只需要显式整数编码，标准库 `to_le_bytes` / `from_le_bytes` 也足够，不必为了少量头字段强行增加依赖。[版本文档](https://docs.rs/bytemuck/1.25.2/bytemuck/)

### serde + postcard：放在适配层

Serde 提供序列化/反序列化 trait 框架，本身不规定字节格式。TOML 配置适合使用它；不建议把 `Serialize + Deserialize` 强制加到所有热点 Value 上，因为原 FasterKv 允许自定义大小和原地原子修改。[Serde 文档](https://docs.rs/serde/1.0.229/serde/)

Postcard 自 1.0 起声明稳定 wire format，但格式不自描述，收发双方仍需共享 schema；宽整数和长度采用 varint。它适合控制面结构或可选值 codec，不能自动提供字段演进或原地更新。若采用，建议评估关闭默认 feature 并启用 `alloc`，外层保留 RasterKV 格式/schema 版本和长度限制。[Postcard 文档](https://docs.rs/postcard/1.1.3/postcard/)、[格式规范](https://postcard.jamesmunns.com/wire-format)

### rkyv：保留为可选归档方案

`rkyv` 提供零拷贝归档和验证能力，格式受字节序、对齐、指针宽度等 feature 控制。即使启用验证，也不会把 archived 对象变成符合 RasterKV 原地并发更新协议的 Value。建议只在不可变对象/用户 codec 确有需求时评估，不作为 HybridLog 默认布局。[版本文档](https://docs.rs/rkyv/0.8.18/rkyv/)

### bincode：排除默认选择

RustSec 的 `RUSTSEC-2025-0141` 是 **INFO Unmaintained** 公告，明确团队停止开发；它不等同于证明每一个历史版本存在可利用漏洞。本轮还直接读取 crates.io 的 3.0.0 发布包，发现 `src/lib.rs` 仅含 `compile_error!`，因此注册表最高稳定版本不是可接入实现。不建议为新的独立文件格式采用它，也不建议只因为教程使用广泛而默认选择 1.x/2.x。[RustSec 公告](https://rustsec.org/advisories/RUSTSEC-2025-0141.html)、[官方发布包](https://crates.io/api/v1/crates/bincode/3.0.0/download)

## 4. 哈希与校验

`xxhash-rust` 提供 XXH32/64 和 XXH3，算法通过 feature 选择，默认不启用算法。建议评估 `xxh3` 的明确字节输入接口，固定算法标识、编码规则及种子，保留自定义哈希接口。它是非密码学哈希，不能把高吞吐当作对抗恶意碰撞的保证；对不可信 key 的需求需要另行选择 keyed 方案。[版本文档](https://docs.rs/xxhash-rust/0.8.18/xxhash_rust/)

**持久化哈希不能直接依赖通用 Rust `Hash` 的字节喂入规则。** 标准库明确该输入不保证跨平台或编译器版本可移植；aHash 也明确不同机器/版本可能产生不同结果。对于检查点中保存的桶与 tag，恢复必须使用相同哈希语义，或明确重建整个索引。`ahash` 仅作为非持久化辅助表候选。[Rust Hash 可移植性](https://doc.rust-lang.org/std/hash/trait.Hash.html#portability)、[aHash 文档](https://docs.rs/ahash/0.8.12/ahash/)

上游 key 的 `GetHash()` 可自定义，仓库另有 `Utility::FasterHash`；既然用户不要求旧文件兼容，就不必以复用上游 hash 字节为目标，但相等 key 必须得到相等 hash，恢复前后也必须一致。[上游 utility.h:41](https://github.com/microsoft/FASTER/blob/321d872eabda6a0345c8bd76419f89723ed864ae/cc/src/core/utility.h#L41)、[上游 key_hash.h:17](https://github.com/microsoft/FASTER/blob/321d872eabda6a0345c8bd76419f89723ed864ae/cc/src/core/key_hash.h#L17)

`crc32c` 实现 CRC-32C/Castagnoli，并利用部分平台硬件指令。可用于独立格式的记录、页面或元数据校验；应先决定覆盖粒度和写入顺序。CRC 不证明记录完整提交，不代替 checkpoint version、commit marker 或崩溃恢复协议；32 位碰撞也不适合作安全认证。[版本文档](https://docs.rs/crc32c/0.6.8/crc32c/)

| `uuid` | 开 `v4` 为会话和检查点创建标识；按需开 `serde` | 官方支持解析/格式化及按 feature 开启生成；写入固定的 16 字节表示，并定义 nil 与文本语义，不序列化私有结构布局。[文档](https://docs.rs/uuid/1.26.0/uuid/) |

## 6. 文件格式建议与实施边界

以下是基于独立格式决定的设计输入，尚未冻结具体格式：

1. 固定头字段使用显式位宽、字节序和位掩码；逻辑地址与内存指针分离，禁止持久化裸指针或 Rust 对象镜像。
2. 元数据包含 magic、格式/schema 版本、哈希标识、必要种子、索引/日志版本、会话序号及长度；用户 codec 也需版本标识。
3. 活跃可变内存记录与稳定磁盘字节视图分开建模，编码层不强迫取消原地更新；刷盘和恢复按照协议生成/校验一致的磁盘记录。
4. 用户变长键值需要明确长度、对齐、所有权、原子访问和追加回退；不因为选了 serde 或 rkyv 就缩减这部分功能。
5. 当前 direct dependencies 的声明只能给出 MSRV 下界；例如 uuid/toml 已声明 1.85，而验证组合中的 criterion 还要求 1.86。实际工程需基于目标平台和 Cargo.lock 编译后再承诺 MSRV。

本轮已读取 crates.io 元数据、官方 API 文档、RustSec 公告及 bincode 发布包；没有执行 crate 代码、编译、测试或性能试验，没有创建 Cargo.toml/Cargo.lock。版本表是调查快照，不是锁定依赖清单。
