# RasterKV 第一阶段范围与支持库选型

更新日期：2026-09-10。本文记录本轮用户确定的目标，并汇总 crates.io 支持库调研。**范围与名称已确认；具体库组合是调研建议，尚未通过原型、编译或性能验证。**

## 1. 已确认的目标

- 仓库名称保持 `raster`，本项目的存储对象命名为 **`RasterKV`**。
- 第一阶段完整复刻 FASTER C++ **`FasterKv` 的功能与行为**，不是只做内存 HashMap 或基础 CRUD。
- **使用独立文件格式**，不要求直接读取 C++ FasterKv 的日志和检查点。这一点已由用户在本轮明确确认。
- F2 等高级能力后置；现有源码调查中的 `FasterKv`、`F2Kv` 名称仍表示上游真实符号，不做全局替换。
- 第一期正式验收平台已确认：**Linux + macOS 基础本地文件后端**；Windows 和 io_uring 后置，完整执行顺序见 [14 实现计划地图](14-RasterKV第一期实现计划地图.md)。
- 原调研轮次只产生文档；目前已建立 Cargo 工程与模块骨架，存储算法尚未实现，见 [13 模块骨架](13-模块基础骨架.md)。`RasterKV` 对象名称不等于已取得 crates.io 包名；将来发布的 package 名称需单独核查。

上游行为基线仍是提交 `321d872eabda6a0345c8bd76419f89723ed864ae`，详见 [功能与 API 契约](03-功能与API契约.md)。独立文件格式允许重新设计编码，并不减弱恢复正确性、会话持续性或原地更新等要求。

## 2. 第一阶段功能清单

| 范围 | 第一阶段要求 | 支持库能承担的部分 |
| --- | --- | --- |
| RasterKV 与配置 | 泛型键/值、设备与索引扩展边界；配置对象、TOML 文件/字符串构造、合理默认值 | `serde`、`toml`；实际配置语义自行实现 |
| 单键操作 | Read、Upsert、RMW、Delete，缺失键与墓碑、条件创建、原地失败后的追加回退 | 状态及错误类型可用 `thiserror`；算法自行实现 |
| 用户上下文 | 定长/变长键值、键哈希与相等性、原子/非原子访问、异步结果所有权 | 编码辅助可用 `zerocopy`；安全并发契约自行定义 |
| 会话 | 开始/继续/结束、GUID、单调操作序号、线程归属、当前与前一版本上下文 | `uuid`；会话注册与阶段推进自行实现 |
| 异步完成 | 即时结果与 Pending、轮询推进、重试、排空、一次完成、错误清理 | `crossbeam-queue`；I/O 适配层与请求生命周期自行实现 |
| 内存哈希索引 | tag、溢出桶、冲突链、原子发布、在线扩容、检查点恢复 | `std::sync::atomic`、`crossbeam-utils`；不能用通用 map 直接替换 |
| 混合日志 | 可变/过渡/只读区、循环页、磁盘区、变长补读、刷盘与安全回收 | 对齐分配库、系统 I/O；页状态与地址边界自行实现 |
| 本地设备与空设备 | Null/内存测试设备，本地分段文件、偏移读写、持久化、截断、故障传播 | `std`、`rustix`、可选 `io-uring` / `windows-sys` |
| 检查点与恢复 | 完整/索引/日志检查点、token、版本、会话持久化序号、恢复重放与继续会话 | `uuid`、显式格式；库不会提供 FASTER 协议 |
| 日志维护 | Compact、查索引压缩、自动压缩、ShiftBeginAddress、GC 与并发操作交错 | 线程与队列原语；正确性算法自行实现 |
| 读缓存 | 缓存命中、索引地址标记、失效、淘汰及主日志衔接 | 仍属第一阶段，不能仅因名称含“缓存”而后置 |
| 扫描与诊断 | 日志记录扫描/缓冲模式、地址与日志跨度、会话和压缩状态、分布及统计输出 | `tracing` 和测试工具；`Size` 仍不等于有效键数 |
| 验收 | 内存/磁盘同等结果、并发更新、分页、恢复、压缩、扩容、缓存和变长记录 | `loom`、`proptest`、`tempfile`、`criterion` 与自建差分/故障测试 |

该清单从 [上游公开 API](03-功能与API契约.md) 和 [核心架构](02-核心抽象与架构.md) 映射而来。Rust 方法拼写、借用形式和错误枚举可以更符合 Rust，但要逐项说明行为对应关系。上游已定位的错误不作为必须复刻的行为。

## 3. 后续 TODO 与边界

- [ ] F2 热冷双存储组合、跨层读写/墓碑、迁移和组合检查点。
- [ ] `ColdIndex` 的嵌套可落盘索引实现及其 F2 组合；第一阶段保留索引可替换契约，默认内存索引的能力必须完整。
- [ ] 跨 store 的条件插入和 `to_other_store` 压缩模式，随 F2 一起实现；单 store 查找式压缩仍在第一阶段。
- [ ] Azure Blob 等远端设备扩展：作为高级后端调研与实现项，基础设备契约须保留。
- [ ] Windows 原生后端及 Linux io_uring 后端：已由用户确认后置，基础设备协议保留适配能力。
- [ ] 面向 Tokio/其他运行时的可选 async 外观：不作为第一阶段核心引擎的强制依赖，也不代替原有 Pending 推进能力。

独立文件格式已确定，C++ 磁盘格式兼容不属于第一阶段要求。Linux 与 macOS 都需原生运行基础文件后端并通过第一期验收；Windows 和 io_uring 的后置不影响单 store 功能完整性要求。

## 4. 推荐的支持库组合

以下是分层引入顺序，不建议一次性全部写进 dependencies。每个版本、MSRV、许可证及一手资料见三份专题文档。

| 层次 | 建议候选 | 采用判断 |
| --- | --- | --- |
| 基础并发 | `crossbeam-utils`、`crossbeam-queue` | 优先：缓存行隔离、退避和完成队列，保留自有索引/页协议 |
| 错误与标识 | `thiserror`、`uuid`（v4） | 优先：公开类型由 RasterKV 定义，避免泄漏实现依赖 |
| 格式与配置 | `zerocopy`、`serde`、`toml` | 优先：固定格式辅助和 TOML；不要求所有用户 Value 都是 Pod/FromBytes |
| 本地设备基线 | `std::fs` / 平台 FileExt + 必要的 `rustix` + 工作线程 | 推荐先验证：在设备层提供拥有请求和完成队列，核心不绑定 runtime |
| Linux 完成式 I/O | `io-uring` + 对齐缓冲包装 | 推荐优化候选；缓冲存活、CQE、失败与取消由设备适配层保证 |
| 跨平台完成式 I/O | `compio-driver` + `compio-buf` | 强备选：可手工推进，但线程归属及 Windows 句柄绑定必须验证 |
| 对齐内存 | `aligned-vec` 或 `std::alloc::Layout` 封装 | 二选一验证；对齐大小应由设备能力决定，不能固定猜测 |
| 调试与观测 | `tracing` | 建议按需/feature 开启；订阅器由应用或示例安装 |
| 持久化哈希 | 自有稳定哈希契约，`xxhash-rust` 为默认实现候选 | 输入使用明确编码，固定算法标识和种子；允许用户替换 |
| 校验 | `crc32c` | 可选独立格式增强；需规定覆盖范围，不替代提交/恢复协议 |
| 非核心同步 | `parking_lot`、`crossbeam-channel` | 仅在控制面或设备线程确有需要时引入 |
| 验证与基准 | `loom`、`proptest`、`tempfile`、`criterion` | 开发依赖；`shuttle`、`fail` 可按验证缺口补充 |

来源与比较：[存储与 I/O 支持库调研](06-存储与IO支持库调研.md)、[并发与验证支持库调研](07-并发与验证支持库调研.md)、[格式与通用支持库调研](08-格式与通用支持库调研.md)。上述“优先”均是结合一手资料与 RasterKV 需求的工程判断，不是实测排名。

## 5. 不宜直接引入的替代方案

- **通用并发 Map 替代核心索引**：其哈希桶、扩容、回收和内存布局与日志地址/检查点协议不同。可用于测试参照或辅助表，不能据此完成 RasterKV 索引。
- **`crossbeam-epoch` 替代整个 LightEpoch**：它提供安全延迟回收，不能同时提供会话版本、页面安全边界和检查点阶段完成判断；本轮建议暂缓，防止双重 epoch 协议。
- **将 Tokio 作为全局强制运行时**：会话线程和自主推进协议需要适配，`tokio::fs` 当前也依赖阻塞线程池，不能因 API 是 async 就认定为原生完成式磁盘 I/O。
- **`memmap2` 直接替换混合日志**：页缓存映射不提供原来的页窗口、拥有 I/O 请求和版本检查点协议。
- **`bincode` 默认作为新格式基础**：已查到停止维护公告；crates.io 的最高稳定版本并不自动代表可用候选，详见格式专题。
- **将可变日志值统一归档为 `rkyv` 对象**：应先证明能保持原地原子更新与变长生命周期契约，本轮不列为核心默认依赖。

各项依据及来源位于对应专题；它们针对当前架构，不是对库的一般性质量判断。

## 6. 下一步选型验证应产生的证据

1. **设备小验证**：同一设备接口下跑工作线程后端与完成式后端，覆盖偏移读写、短读短写、flush、截断、关闭时的在途请求；确认完成回调回到正确会话。
2. **内存小验证**：索引 CAS + 日志页回收最小模型，用 Loom 检查交错，并用 Miri/单元测试验证不含实际 OS I/O 的 unsafe 边界。
3. **格式小验证**：明确头部、长度、版本、算法标识、校验和与提交记录；保留跨重启/跨架构固定字节样例，不使用 Rust 对象内存镜像作为格式。
4. **依赖闭包验证**：选定 target/features 后生成真实 Cargo.lock，再核对 MSRV、许可证和 advisory；单个 crate 声明的 MSRV 不代表整个组合的 MSRV。
5. **行为对照**：按第一阶段矩阵迁移上游场景，覆盖 Pending、恢复序号、读缓存、压缩竞态和索引扩容后，再评估性能。

以上是原调研轮次提出的验证建议，当时未运行、未引入依赖。当前工程仍为零外部依赖的骨架；后续验证和实现统一按 [14 实现计划地图](14-RasterKV第一期实现计划地图.md) 记录，不以此处调研建议充当完成证据。
