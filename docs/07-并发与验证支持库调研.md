# RasterKV 并发与验证支持库调研

调研日期：2026-09-10。目标是第一阶段完整实现 C++ `FasterKv` 对应的 **RasterKV**；F2、多层冷热存储及冷索引属于后续 TODO。用户已确认采用独立文件格式，以功能与行为一致为目标，无需读取 C++ 原有文件。本文件是选型建议，不表示已经引入依赖、完成兼容验证或获得性能结果。

## 1. 建议结论与自研边界

建议优先采用 `crossbeam-utils`、`crossbeam-queue`；开发验证采用 `loom`、`proptest`、`tempfile`，基准建立时加入 `criterion`。`parking_lot` 和 `crossbeam-channel` 按控制面、设备线程需求引入。暂缓 `crossbeam-epoch`、`arc-swap`、`shuttle`、`fail`；`papaya`、`scc` 不适合直接替代主索引。

这里的判断基于本仓库的 [核心抽象与架构](02-核心抽象与架构.md)、[API 契约](03-功能与API契约.md) 及原源码。第一阶段必须自行保持以下语义：

| 原实现职责 | Rust 实现边界 |
| --- | --- |
| `LightEpoch` 的线程保护、安全 epoch、延迟动作 | 自行实现参与者注册、推进、安全边界与动作生命周期；不能仅用一个垃圾回收库顶替 |
| `Refresh` 和检查点阶段 | 会话版本、序号、前后执行上下文、阶段确认及待完成请求排空仍由 RasterKV 协调 |
| 64 位桶项及 CAS 发布 | 使用标准库 `AtomicU64` 表达地址、标记和发布语义；支持平台须具备相应原子能力 |
| 用户 `GetAtomic` / `PutAtomic` / `RmwAtomic` | 设计清晰的值同步接口；索引 CAS 或 epoch 均不能使普通可变值读写自动安全 |
| 线程会话 | 活跃会话继续采用线程归属；建议以不能任意跨线程移动的句柄表达，不因引入 async 库而允许迁移 |

原源码依据：[light_epoch.h:172](https://github.com/microsoft/FASTER/blob/321d872eabda6a0345c8bd76419f89723ed864ae/cc/src/core/light_epoch.h#L172)、[light_epoch.h:215](https://github.com/microsoft/FASTER/blob/321d872eabda6a0345c8bd76419f89723ed864ae/cc/src/core/light_epoch.h#L215)、[hash_bucket.h:89](https://github.com/microsoft/FASTER/blob/321d872eabda6a0345c8bd76419f89723ed864ae/cc/src/index/hash_bucket.h#L89)、[faster.h:733](https://github.com/microsoft/FASTER/blob/321d872eabda6a0345c8bd76419f89723ed864ae/cc/src/core/faster.h#L733)。上述 Rust 边界为适配分析，不是这些 crate 提供的保证。

## 3. 并发原语与回收

### 3.1 Crossbeam：精选子包，避免一次性引入全部组件

| 包 | 决策 | 可用 API 与接入点 | 边界 |
| --- | --- | --- | --- |
| `crossbeam-utils` | 推荐 | `CachePadded<T>` 隔离参与者槽和热点计数；`Backoff` 用于 CAS 重试 | 内存填充不定义磁盘格式，也不证明实际 CPU 上无伪共享；退避不保证等待阶段必然完成 |
| `crossbeam-queue` | 推荐 | `ArrayQueue<T>` 用于有界完成队列；`SegQueue<T>` 用于确实允许动态增长的场景 | 队列不能替代 pending 请求所有权、一次完成及退出排空协议；有界队列满必须有显式处置，不能丢完成事件 |
| `crossbeam-channel` | 按需推荐 | `bounded`、`try_send`、`try_recv` 用于设备工作线程和通知 | 阻塞 `send` 可能令参与 epoch 的线程无法推进；发送端断开不代表持久化成功；不必同时为同一完成通道使用 queue 和 channel |
| `crossbeam-epoch` | 暂缓 | `Collector`、`LocalHandle`、`Guard`、`Atomic`、`defer` 可服务独立的堆对象回收 | 原始日志逻辑地址不是 `Atomic<T>` 指针；不能将其回收 epoch 等同于 RasterKV 的页安全边界或检查点版本 |

一手 API：[utils](https://docs.rs/crossbeam-utils/latest/crossbeam_utils/)、[queue](https://docs.rs/crossbeam-queue/latest/crossbeam_queue/)、[channel](https://docs.rs/crossbeam-channel/latest/crossbeam_channel/)、[epoch](https://docs.rs/crossbeam-epoch/latest/crossbeam_epoch/)。维护仓库：[crossbeam-rs/crossbeam](https://github.com/crossbeam-rs/crossbeam)。

`crossbeam-epoch` 的核心是 pin 期间保护对象，等待足够的 epoch 推进后回收。即使 `defer` 可以登记任意延迟函数，也没有直接提供 FASTER 的参与会话确认、检查点阶段机、持久化序号和安全刷盘边界。因此建议先复刻一个可单独测试的 RasterKV epoch 协调器；只有出现独立堆对象回收需求时，再判断是否引入该包。长期 pin 和会话长期不刷新均应设进度测试，但两者的状态机不能混为一谈。[epoch 官方说明](https://docs.rs/crossbeam-epoch/latest/crossbeam_epoch/)

原桶项原子操作没有显式指定 C++ 内存序。移植建议先保留顺序一致性语义，再以模型和实测决定优化；不能因为第三方队列内部采用更弱内存序，就整体下调日志发布、读取和回收的内存序。普通 Rust `&mut V` 也不能同时交给多个 Atomic 回调；必须定义内部可变性、同步责任和引用有效期。

### 3.2 锁与只读快照

| 包 | 决策 | 适用点与限制 |
| --- | --- | --- |
| `parking_lot` | 按需推荐 | `Mutex` / `RwLock` / `Condvar` 适合控制面状态、设备注册和测试设备；主索引不能因此变成整表锁。其 Mutex 不采用标准库相同的 poisoning 行为，panic 后状态恢复必须明确设计 |
| `arc-swap` | 暂缓 | `ArcSwap<T>` 适合读多写少的不可变配置快照；不是 64 位日志地址 CAS 的替代物。无需动态配置时直接用不可变配置和 `Arc` 即可 |

一手依据：[parking_lot API](https://docs.rs/parking_lot/latest/parking_lot/)、[Mutex 差异](https://docs.rs/parking_lot/latest/parking_lot/type.Mutex.html)、[arc-swap API](https://docs.rs/arc-swap/latest/arc_swap/)。`arc-swap` 官方文档明确记录 1.9 修正了此前过弱的内存序，并可能影响性能；因此不能用旧性能文章推断当前版表现。维护仓库：[parking_lot](https://github.com/Amanieu/parking_lot)、[arc-swap](https://github.com/vorner/arc-swap)。

## 4. 完整并发 Map：可比较，不作为主索引替身

| 包 | 决策 | 可用能力 | 与 RasterKV 的差距 |
| --- | --- | --- | --- |
| `papaya` | 主索引不适配；外围结构暂缓 | 并发 `HashMap`，pin 保护访问、原子更新、增量扩容 | 管理自身键值和回收；迭代是弱快照；更新闭包可能重试；这些语义不能直接实现日志地址链、invalid 记录、索引检查点和恢复 |
| `scc` | 主索引不适配；外围结构暂缓 | `HashMap` / `HashIndex` / `HashCache`，同步和异步接口 | 这里的 `HashIndex` 是通用并发容器，不是 FasterKv 的 `MemHashIndex`；自有桶布局、扩容、回收与 RasterKV 持久化协议仍需衔接 |

一手依据：[papaya 文档](https://docs.rs/papaya/latest/papaya/)、[papaya 仓库](https://github.com/ibraheemdev/papaya)、[scc 文档](https://docs.rs/scc/latest/scc/)、[scc 当前包登记的仓库](https://codeberg.org/wvwwvwwv/scalable-concurrent-containers/)。这些包可以用于独立元数据映射或性能对照；本轮不建议为尚不存在的外围需求引入它们。不能把通用 Map 的快照迭代或序列化认定为完成 RasterKV 检查点。

## 5. 验证与基准

| 包 | 决策 | 第一阶段用法 | 不覆盖的部分 |
| --- | --- | --- | --- |
| `loom` | 推荐开发依赖 | 对桶项 CAS 发布、epoch 安全边界、完成一次性协议建立少量线程的小模型 | 必须替换原子、锁、线程及相关 `UnsafeCell` 等原语；不自动检查外部 crate 内部行为，也不完整覆盖所有弱内存重排 |
| `proptest` | 推荐开发依赖 | 生成键值、变长长度及操作序列，对照简单顺序模型；失败用例收缩与回归 | 不会自行建立线性化判定或持久化规范；异步 `Pending` 不能当作最终成功 |
| `tempfile` | 推荐开发依赖 | `TempDir` 隔离日志和检查点目录；恢复测试控制目录的保留与删除时机 | 不模拟掉电；子进程终止可能不运行析构，测试控制进程要拥有目录生命周期 |
| `criterion` | 基准建立时推荐 | `BenchmarkGroup` / `Throughput` 评估索引访问、热日志读取、更新、RMW | 微基准不代表完整存储吞吐或 P99；设备、数据集、键分布、命中率、checkpoint 开销须另设端到端负载 |
| `shuttle` | 暂缓，扩大并发验证时采用 | 随机调度、PCT、失败调度重放，覆盖比小型 Loom 模型更大的协议交错 | 同样要替换并发原语；通过随机测试不证明正确，也不替代弱内存模型测试 |
| `fail` | 暂缓，设备故障模型不足时采用 | 用具名 failpoint 在检查点阶段或 IO 完成边界注入返回、暂停等故障 | 需启用 `failpoints` 并管理测试配置；不能自动模拟掉电、缓存丢失或 torn write；稳定版较旧，MSRV 未声明 |

一手依据：[Loom 限制](https://docs.rs/loom/latest/loom/)、[Proptest](https://docs.rs/proptest/1.11.0/proptest/)、[Tempfile](https://docs.rs/tempfile/3.27.0/tempfile/)、[Criterion](https://docs.rs/criterion/0.8.2/criterion/)、[Shuttle](https://docs.rs/shuttle/latest/shuttle/)、[Fail](https://docs.rs/fail/0.5.1/fail/)。维护仓库分别为 [tokio-rs/loom](https://github.com/tokio-rs/loom)、[proptest-rs/proptest](https://github.com/proptest-rs/proptest)、[Stebalien/tempfile](https://github.com/Stebalien/tempfile)、[criterion-rs/criterion.rs](https://github.com/criterion-rs/criterion.rs)、[awslabs/shuttle](https://github.com/awslabs/shuttle)、[tikv/fail-rs](https://github.com/tikv/fail-rs)。

建议一开始就保留很小的内部并发原语适配层，以便在模型测试中选用 Loom 类型。外部队列可用测试替身验证 RasterKV 协议，但这种结果只覆盖替身和协议；生产版本的跨库集成仍需真实多线程测试。Loom 通过不能被写作“已证明全部 RasterKV 无数据竞争”。

建议首先验证四类具体不变量：

1. 发布成功的地址只指向已初始化记录；CAS 失败的新记录不能作为有效最新值返回。
2. 最慢活跃会话尚未越过边界时，相应页不能回收；会话退出能撤销保护并排空待完成工作。
3. 每个挂起请求只终结一次；IO 错误、重试和关闭交错不得产生重复回调或遗失上下文。
4. 恢复结果遵守已完成检查点的会话序号契约；检查点中途错误不能被计为持久化完成。

这些测试目标来自 RasterKV 原实现协议，不是测试框架默认提供的性质。恢复测试还需独立的可控设备实现和进程级故障测试；将 `fail` 放到函数入口不足以替代它们。

## 6. 最小集合与后续核验

建议第一批运行时支持只选 `crossbeam-utils` 与 `crossbeam-queue`，其余使用标准库；开发依赖选 `loom`、`proptest`、`tempfile`，建立基准时加入 `criterion`。若设备模型需要线程阻塞等待，则以 `crossbeam-channel` 实现该通道，而不是为同一职责重复堆叠两个队列库。锁先按控制面实际需要选择标准库或 `parking_lot`。

实施前应完成固定版本和 feature 集合的构建、实际 MSRV 检查、传递依赖审查；实现后需要针对真实工作负载评估开销。当前没有编译、压测、平台兼容和端到端正确性结果。F2 及冷索引后置不会降低上述 RasterKV 检查点、恢复、会话和日志安全边界的第一阶段要求。
