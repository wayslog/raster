## 同进程资源循环的预设门槛

运行前固定为 8 轮预热、64 轮测量。每轮直接复用公开 `disk_lifecycle` 流程：40 个键、变长值/墓碑、三类检查点、两次恢复续接、扩容、三种扫描缓冲、两种压缩、工作段回收及旧检查点释放。每轮创建独立目录，成功后销毁对象并清理；业务失败保留材料。全部循环在同一进程，不能用反复启动子进程掩盖泄漏。

每轮结束都与预热后的固定基线比较，任一超限即失败，不在观察到结果后提高门槛：

| 指标 | 允许增长 |
| --- | --- |
| 仍存活的 Rust 分配字节 | 256 KiB |
| 仍存活的 Rust 分配块 | 16 个 |
| 文件描述符 | 2 个 |
| 线程 | 1 个 |
| 本进程 RSS | 16 MiB |

验收二进制单独安装委托 `System` 的计数分配器；库不安装全局分配器。计数覆盖 Rust 分配、清零、调整大小和释放，不将系统分配器保留的空闲页当作存活对象；RSS、句柄和线程另从本进程读取。分配器正确性由独立局部计数测试验证。多字段计数只在业务线程已退出、对象已销毁的边界采样；分配峰值是整个进程至今的峰值。

```sh
cargo test --locked --all-features --test p9_allocator
RASTER_RESOURCE_OUTPUT=target/p9-resources/resources.csv cargo run --locked --release --all-features --example resource_cycles
```

CSV 及数据目录必须全新，不覆盖已有文件。以下分别记录本地与原生 CI 结果。该检查不代替故障注入，也不是对任意运行时长或硬件故障的保证。

## 性能复核起点

原有阈值继续使用 [P3 内存性能基线](P3内存性能基线.md)：同机器、同工具链、同输入与计时方式，吞吐下降超过 25% 或 P99 上升超过 30% 时复核。

在同一 Apple M1 Pro、16 GiB、macOS 26.5.2、Rust 1.98.1 上，将 P3 提交 `7f2f03b` 与当前 `5306931` 使用完全相同的 200,000 次 Upsert 驱动对照，每组各三次。八组均触发原阈值。缩为单线程单键原子 Upsert，交替运行顺序的三轮复核中，当前吞吐为旧版的 0.333/0.278/0.305，P99 为 2.404/2.803/2.606；业务结果均成功校验。原始数据位于 `target/p9-perf-pair-002` 至 `005`，不计入首次驱动输出次数未同步的无效 `001`。

提交二分的首个变慢提交为 `fd122313ba343ed4b50ebcd0508eb2627833da1b`（Upsert 容量等待与一次性替换结果），父提交 `26040aa2` 未触发阈值。每个候选与旧版交替测量各九个样本，证据在 `target/p9-perf-bisect-evidence/`。采样进一步观察到完成邮箱插入/删除、分配、版本许可和可变区查询开销；主线程等待和嵌套样本不能重复计入 CPU 成本。

仅把完成邮箱的 BTreeMap 换成 HashMap 的隔离实验吞吐为基线的 1.023 倍，收益不足以解决原问题，已撤销，未改生产实现。性能复核尚未完成；后续仍需完整内存/超内存、读写分布、多线程、I/O 放大、内存与恢复耗时报告，不能以基准程序退出成功宣称性能通过。
