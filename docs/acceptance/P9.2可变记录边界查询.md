# P9.2 可变记录边界查询

状态：成对性能测量、完整本地检查及指定提交的 13 个原生交付任务均已通过。旧 P3 总体性能复核和 P9.1 删除返回契约仍未完成。

## 改动与安全边界

[成本诊断](P9.2同步路径成本诊断.md)在调用栈中定位了 find_mutable → frontiers → PagePool::tail。源码确认该查找只用 begin、read_only 和 head 判定记录是否仍可修改，通用边界快照却额外读取未使用的 tail，并取得页分配器锁。

现在只在原日志边界锁内复制已有边界，同时检查页池的中毒标志；正常查找不访问分配器内部状态。循环每一跳仍重新观察 begin/read_only/head，页内逻辑截断仍优先于较落后的只读边界。记录租约、值许可和检查点版本检查不变。租用失败时，原有 RangeTruncated 分支仍重新读取完整边界，以识别 head 已推进的竞争；其他错误继续传播。

中毒检查拒绝已观察到的页池故障，并不等待正在分配的线程，也不承诺检查之后不会出现其他线程的故障。原 tail 锁在返回后同样不覆盖后续记录访问。记录字节由独立租约和访问许可保护；这次优化没有从页池未受锁保护的可变状态取数据，没有删除真正的记录访问仲裁。公开 frontiers 仍返回实时 tail，分配、冻结、刷盘、淘汰与逻辑截断的边界更新逻辑不变。没有新依赖、unsafe、文件格式或公开 API 变化。

## 契约与交付检查

三个测试首先在原生产实现上运行并通过，验证待保持的行为：

- 同页碰撞链中，begin 推进后找不到被截断旧键，但仍能访问存活键；冻结后不再返回可变记录，冻结前取得的租约也不能继续更新。
- 冷恢复 head 之前的历史链返回无可变记录；可变区缺失记录返回 RangeTruncated，驻留键仍可正确读取。
- 分别毒化页池、日志边界和记录表后，find_mutable 返回对应的原 InvalidState 错误。

优化后的格式、全部特性全目标 Clippy、426 个运行测试、9 个 doctest、示例编译和严格 rustdoc 通过。40 个故障入口及 32 组完整历史也通过，既有冻结争用、挂起写入、检查点恢复与逻辑截断回归继续执行。主要本地日志已去除私人路径并纳入归档；原过程位于 target/p9-mutable-boundary-experiment/。此次没有新 unsafe 或布局改动，未把旧 Miri 结果计作本次重新执行。指定提交的原生结果见下表。
