# P9.2 同步写入分配优化

状态：本次分配优化已完成本地与双平台原生交付验证；旧 P3 性能回退及 P9.2 总体验收仍未完成。基线为 `50142b68f3fe724393124c904dfa9e62cd69dbb3`，开发及 MSRV 保持 Rust 1.98.1。

## 问题与实现

同步 Upsert 过去先建立 Ticket/Completer 的共享结果槽，执行完成后立即从内部票据取回结果。预热后的单线程原子热点诊断确认，每次操作有 8、16、80 字节三笔分配；其中共享结果槽的 80 字节分配在同步路径不需要长期保留。

现在初次推进仍在接受前检查并预留结果预算、请求身份及版本许可，再接受操作序号。UpsertTask 初始不持有完成端；若已有最终结果，统一清理准备值和用户请求、记录原有统计及 I/O 计数，再直接转交 Ready。只有真正需要继续推进时，才以原身份和预算建立 Ticket/Completer 并加入会话任务表。异步终结继续使用原完成槽。

错误、panic、NotApplied/Applied/Unknown、失败关闭和请求析构仍共用原收尾规则。没有跳过检查点版本、预算或序号协议；没有改变公开 API、文件格式、依赖或生产 unsafe。通用 Completer 的结构未改，避免将输出类型的大小扩散到其他操作任务。

## 实验口径与结果

本地 macOS 26.5.2 / APFS、Apple M1 Pro（10 个物理和逻辑 CPU，16 GiB），Rust 1.98.1 aarch64-apple-darwin，全部特性、release。与既有 P3 复核使用同一份 200,000 次操作驱动，分别覆盖原子整数/变长值、256 键均匀/共享单键热点、1/4 线程；每次进程运行各三轮。全部步骤验证真实同步结果，拒绝只对 Busy 保留请求与序号重试。

基线、候选按 AB/BA/BA/AB 顺序执行，每端每组共 12 个样本；没有同时运行构建、测试或 Miri。原始第一批曾出现原子四线程热点 P99 比 1.344，保留在样本 0、1 中；随后按预先安排加入反序样本 2、3，并合并全部数据，不删去触发复核的样本。

六组吞吐改善，两个四线程均匀组下降约 7%—10%；全部合并结果未触发吞吐下降 25% / P99 上升 30% 的既定复核线。不能据此断言所有负载都变快，也不能将共享热点的调度变化解释成稳定的公平性保证。相对旧 P3 的总体回退仍待处理。

独立分配诊断只统计预热 128 次后的 200,000 次同步热点写入：基线 600,000 次成功分配、20,800,000 字节，候选 400,000 次、4,800,000 字节；原每次 8+16+80 字节变为 8+16 字节。该口径是累计分配事件及请求字节，不是 RSS 或存活内存；计数器的原子成本不用于吞吐对比。

曾测试把通用 Completer 改为内联/共享枚举，虽有局部收益，但会使其布局包含泛型输出，因而没有采纳。该实验与最终直接转交版本分开保存，不能混用其性能数字。

## 复现与证据

[归档目录](data/p9-ready-experiment/manifest.json) 保存八份原始计时 CSV、两份分配 CSV、两组单线程补充实验摘要、二进制及文件哈希、同一份 [200,000 次驱动](data/p9-ready-experiment/driver.rs)、[分配探针](data/p9-ready-experiment/allocation_probe.rs)和[计时补丁](data/p9-ready-experiment/candidate.patch)。补丁基于 50142b6；新增的两个 cfg(test) 所有权用例在计时后加入，不改变运行路径。两份 Rust 文件是诊断输入快照，不是新增库入口。

使用两个隔离检出，基线保持 50142b6，候选以 `git apply --unidiff-zero` 应用上述补丁；将同一 driver.rs 复制为各自 examples/memory_matrix.rs，分别执行 `cargo build --locked --release --all-features --example memory_matrix`。执行各自 target/release/examples/memory_matrix 时清除 RASTER_PERF_HOT_ONLY，按 AB/BA/BA/AB 顺序保存八份输出。每次进程内部跑三轮，共形成每端每组 12 个样本。分配探针另复制为 examples/allocation_probe.rs，按同样特性与模式构建，计数运行与计时分开。

归档可独立复核：

```sh
python3 tools/acceptance/audit_ready_comparison.py docs/acceptance/data/p9-ready-experiment
```

原始临时输出仍在 `target/p9-direct-ticket-experiment/`；未采纳内联方案的输出在 `target/p9-ticket-experiment/`。归档包含首次触发尾延迟复核的样本，没有覆盖或拼接为单次成功。

## 仍未通过的旧 P3 门槛

以同一 200,000 次单线程原子热点驱动重新构建当前 f0f9725 与 P3 7f2f03b，各运行三轮，业务结果均正确且无拒绝重试。当前吞吐中位数为 2,488,024 操作/秒、P99 459 ns；旧版为 6,730,862 操作/秒、P99 208 ns。吞吐比 0.3696、P99 比 2.2067，仍按原规则以性能复核失败结束。

[原始数据及二进制哈希](data/p9-ready-p3-f0f9725/manifest.json)保留这个结果；本次减少分配不等于满足旧 P3 的总体门槛。下一步继续处理请求准备开销；上游 A02/A05 删除返回契约也仍待决定。
