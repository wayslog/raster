## 公开逻辑截断与工作段删除

`Maintenance::shift_begin(address)` 接受一个独立 GC 动作，由会话或维护轮询推进。热记录边界错误在接受前拒绝；冷页内边界通过有界页读取验证，失败报告仍携带零效果。动作冲突返回 Busy，等待超时沿用原票据。

发布逻辑 begin 时取得全部业务仲裁，先规范化缓存头；begin 不能倒退或超过已知尾部，也不能穿过未完成初始化。普通键查询遇到 begin 之前的链返回缺失；物理扫描跨越被截断范围返回 RangeTruncated。已经接受的修改请求完成 I/O 后重新查询索引，不使用截断前的值执行回调。

后台刷盘在 GC 期间只排空既有写入。GC 越过已作废的完整页并释放内存页；首个保留页可以从页内记录边界开始，后续页编码和检查点材料跳过作废前缀。删除范围按页帧的物理偏移计算，只枚举当前实例工作目录中完整位于保留帧之前的已绑定段。

删除任务先摘除段映射，随后依次关闭句柄、删除文件、同步目录。全页帧租约保护短读、跨段读取以及已经进入邮箱但尚未收取的完成。不能立即释放的运行期租约返回 `DeferredByRuntime { begin, end }` 并终结本次动作；该范围说明待回收旧前缀，不是实际删除字节计数。释放读者后可按相同 begin 重新发起。

`GcReport` 分别给出 begin、index_cleaned、deleted_segments 和 physical。deleted_segments 只统计本次经目录同步确认的删除，包括接续上次失败的任务；Completed 表示本次候选工作段已处理，不表示检查点目录已清理。普通错误返回 `GcFailed { begin, index_cleaned, deleted_segments, cause }`，错误报告保留已经发生的效果，未确认计数不证明磁盘没有发生删除。

关闭、删除或目录同步失败后，任务保留原路径、旧句柄和当前步骤。额外轮询不会自动重试；下一次显式 GC 才接续。已经关闭或已经删除的结果允许继续同步。身份损坏及 panic 按失败关闭协议处理，在设备结束前不丢弃未知在途资源。

缓存安装在业务仲裁内重新检查维护状态及源地址。即使较新的同标签链头在 GC 后保持不变，旧键的迟到磁盘值也不能重新装入缓存。新检查点过滤未清完的旧索引头；GC 使旧的自动索引配对失效，用户需先生成新 Index/Full，才能继续生成 Log 检查点。两代已提交恢复集的独立材料均继续保留。

## 页内截断后的 Upsert 修正

交付复查发现，`find_mutable` 原先只检查 read_only/head；逻辑 begin 位于页内时可能先于这两个边界，同标签存活链头仍能带到已截断的旧记录。新增回归先重现“Upsert 报成功，之后读取仍缺失”，再将 begin 纳入可原地更新范围。修正后重新插入旧键必须追加新记录，另一个碰撞键保持不变，旧记录的原地更新回调不会执行。

锁实现可使用固定工具链已有的非阻塞文件锁，避免设备工作线程等待锁而阻塞其他完成；持有方式仍需接入拥有型设备句柄和关闭协议。官方 API 提供 `try_lock`、`try_lock_shared` 和 `unlock`，但克隆句柄重复加锁的行为不能作为独立仲裁依据，后续须使用独立打开的句柄并在两原生平台验证。[Rust File 文件锁文档](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock)

## 已接通目录枚举与跨实例仲裁

设备新增 `ReadDirectory { path, max_entries, max_name_bytes }`，空路径枚举设备根目录，只返回单层拥有型名称和文件类型。名称保留平台字节，符号链接只作为条目报告；名称总字节或条目数量超限时整体失败，不返回可能漏掉依赖的部分目录。结果不是并发快照，释放流程还必须在仲裁内消费。Linux 文件系统与内存设备验证非 UTF-8 名称；本地 macOS/APFS 拒绝非法 UTF-8 创建时，错误如实返回，没有改写名称或产生别名。

`TryLock { path, mode }` 通过独立打开的文件句柄尝试 Shared/Exclusive 锁，成功返回 `Locked(FileId)`，竞争通过完成返回 Busy 且不保留句柄。锁文件以不截断方式打开或创建；协议内不能删除或替换它。锁句柄不接受数据 I/O，Close 和成功 shutdown 先显式解锁再关闭，避免复制/继承描述符延长原锁寿命；进程异常退出由操作系统释放仍持有的锁。底层目录能力继续阻止经路径或符号链接逃出根目录。

DeviceCapabilities 分开声明目录枚举和文件锁能力。原生 Linux/macOS 后端提供两项；内存设备仅提供枚举，不声明进程间锁或持久化能力；Null 均不支持。没有引入新依赖，也没有修改 v1 检查点字节格式。

`checkpoint/catalog_lock.rs` 已接入真实路径，使用根目录 `checkpoint.lock`：

- Full/Index/Log 在材料准备完毕、正式发布之前取得共享锁，持有到 commit 重命名及目录同步完成，并在成功报告前确认关闭。
- Log 在锁内重新读取、验证基准索引的 commit/manifest，再核对恢复匹配关系。基准已失效时不发布新 Log，错误沿用当前检查点失败关闭协议。
- recover 在读取第一个 manifest 前取得共享锁，覆盖两遍材料读取、验证、重放和工作日志同步；实例对外可用前确认释放。
- 后续显式释放使用同一文件的独占锁。单个 Engine 的动作仲裁仍负责实例内互斥，不能代替目录跨实例仲裁。

Busy 仅表示此次尝试未取得锁，允许继续推进；其他错误不当作成功或自动重跑未知效果。失败的检查点保留目录句柄至设备关闭；设备现在会在工作线程全部结束后关闭文件表，不能因设备对象仍存活而永久占锁。
