## 上游固定输入与首次差异

基线：[Microsoft FASTER 321d872eabda6a0345c8bd76419f89723ed864ae](https://github.com/microsoft/FASTER/tree/321d872eabda6a0345c8bd76419f89723ed864ae)。执行器链接原始核心源，不替换上游索引、日志或 CRUD 算法；构建脚本检查提交以及已跟踪文件的干净状态。C++ 输入上下文拥有键、值和异步结果；使用上游浅键/深键协议存储变长键，数字原地更新采用 atomic，字节值增长走追加。

`tests/p9_upstream.rs` 是 Rust 执行端：逐步骤与独立 BTreeMap 模型比较，记录每会话接受序号，再输出真实引擎结果。两端使用同一 `raster-trace 1` 输入和 `raster-results 1` 输出。`tools/upstream/compare.py` 保存完整轨迹、SHA-256、每步输出和差异；存在任何差异即以非零状态结束，没有隐藏差异或放宽为只比较最终值。

首次本地探测使用现有 `p0.trace` 的 8 步边界输入，以及种子 0、1、42、11259375、18446744073709551615 各 1,500 步；随机生成沿用 SplitMix64、每步四个随机数、三个会话和允许跳号的序号。共 7,508 步，读写/RMW 值输出一致，差异如下：

| 观察 | 次数 | Rust 返回 | C++ 返回 |
| --- | ---: | --- | --- |
| 墓碑条件读取 | 15 | tombstone | missing |
| 缺失/重复删除 | 381 | missing | deleted |

固定边界即可复现：空键 upsert 最大 u64，RMW 加一回绕，强制删除，随后 `read(abort_if_tombstone=true)`。Rust 返回墓碑，C++ 返回缺失；同一轨迹的后续普通删除，Rust 返回缺失，C++ 返回成功。

源码解释：上游 [InternalDelete 的可变记录分支](https://github.com/microsoft/FASTER/blob/321d872eabda6a0345c8bd76419f89723ed864ae/cc/src/core/faster.h#L1901) 在链头且无有效前驱时尝试清除索引入口，该优化不检查 force_tombstone；墓碑字节虽然写入，索引查询可能已不能到达。另一些已经删除或链头缺失的路径仍设置/追加墓碑并返回 SUCCESS，是否返回 NotFound 受索引路径影响。这些实测差异不能通过统一忽略 Delete 状态来宣布兼容。

现有 RasterKV 契约在 P0/P3 已固定为缺失删除 NotFound、保留的墓碑条件读取 Aborted(Tombstone)。已向用户确认本期应保留此契约并明确归档两项差异，还是复刻上游路径相关状态；选择尚未取得时，不改写现有契约、不将兼容性标为通过。其余磁盘、恢复、并发和故障工作继续推进。

本次本地 C++ 环境为 Ubuntu 24.04 用户态、GCC 13.3.0，通过 Podman 在 aarch64 虚拟机上运行 x86_64 指令翻译。它能提供早期实测差异，不是原生 x86_64 Linux 验收替身。原始输出位于忽略目录 `target/p9-probe/comparison-1/`，并保留最初非零退出记录；正式 CI 链接待取得后补充。

## 完整历史与恢复

`tests/p9_history.rs` 执行 4 种维护 × 2 种缓存配置 × 4 轮，共 32 组真实文件后端场景。每组先以 2×4096 字节内存日志写入 800 个键，再让两个真实会话线程各自提交一个冷读；断言两个请求均已返回 Pending 后，才接受扩容、Full 检查点、ScanDedup 或 Lookup 压缩。

工作者继续交错执行 RMW、追加替换、删除和读取，记录调用开始、结果返回及真实输出。每组包含 9 个完整区间，独立检查器从初值 7 枚举满足实时先后关系的合法顺序；不是仅校验最终加总。拒绝 Busy 的重试受 60 秒边界限制，已接受操作不重放。维护通过原票据推进，最后由观察会话提交新的 Full 检查点、关闭旧实例、恢复并续接该身份，再次核对终态。

本地该测试实际通过 32 组/288 个事件，耗时约 13.44 秒。此前 p3_history 的检查器正反例和 32 轮内存历史也继续通过。首批原生双平台工程结果已在下文记录；独立故障矩阵还会保存完整历史原始输出。

轨迹执行端另外支持显式检查点边界：`RASTER_UPSTREAM_ROOT` 选择原生文件后端，`RASTER_UPSTREAM_SPLIT` 指定完成第几步后检查点恢复，`RASTER_UPSTREAM_CHECKPOINT` 为 full 或 pair。边界时逐会话确认报告 serial 与 last_accepted 相同，排空、关闭并恢复，然后续接原身份继续后半段。固定 8 步轨迹在第 4 步后分别以 Full、Index+Log 恢复已实际通过；这两次是 Rust 路径验证，尚不是 C++ 恢复对照。

## Linux 执行环境的实际限制与原生接入

本地指令翻译容器能编译上游 Null 和 Linux QueueIoHandler 两种实例，但文件实例启动时 `io_setup` 返回 -38（ENOSYS），上游在创建 libaio 队列时断言退出。该失败不解释为引擎行为错误，也没有通过改写上游后端规避。`ThreadPoolIoHandler` 实际仅在上游 Windows 文件中存在，Linux 应使用 QueueIoHandler；最初选择错误的类型已在正式构建脚本中修正。

新增独立工作流“P9 上游执行环境基线”，在 ubuntu-24.04 原生构建固定上游核心并运行 Null/libaio 两种实例。`tools/upstream/probe.py` 检查各自原始输出是否符合已观察的固定样例，同时保存与 Rust 的两处差异；输出明确标记 compatibility_acceptance=not_completed。它验证可继续开展对照的运行环境，不是容忍差异后宣布 P9 通过。正式对照 `compare.py` 仍在存在差异时返回失败。

## 独立原生矩阵发现的注入竞态

矩阵提交为 `1ffe5ede963e92e07c0a70b3e93cd2a5bbd41162`。[首次独立原生运行 34584045997](https://github.com/wayslog/raster/actions/runs/34584045997) 的 Linux 32 项通过；macOS 在 F30 失败，F01—F29 已通过。F30 输出显示 panic 发生在测试主线程的关闭路径，而不是预期的自动维护推进路径；该运行不能记为双平台通过。

源代码核对表明 F30 同时打开“设备 poll 恐慌”和“完成返回协议错误”两个开关。若自动线程已经经过 poll 开头的 panic 检查，随后读到新打开的协议错误，任务会先失败并退出，未被消耗的 panic 开关留到了主线程 shutdown。因此它还可能只覆盖协议错误而未真正覆盖目标 panic。

修正为独立注入：panic 分支继续扣留完成，等待后台实际消耗一次 poll 恐慌开关后才放开；协议错误分支只注入完成错误。新增断言确认 panic 开关已消耗，并核对协议错误实际发生与否恰好对应当前分支。原有失败状态、失败关闭、维护结果、动作退出和关闭排空断言全部保留。修正后的首次专项运行确认 panic 来自 `raster自动压缩` 线程并被预期收尾。

修正后本地 F30 连续执行 64 次全部通过，每次分别触发协议错误和后台 poll 恐慌，共 128 个注入场景；未扩大截止时间或放宽结果断言。格式及全部特性全目标 Clippy 通过。重复原始输出保留在 `target/p9-f30-repeat/`，原生复核仍以修正提交的新运行结果为准。
