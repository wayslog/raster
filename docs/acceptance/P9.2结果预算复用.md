# P9.2 结果预算复用与热点采样复核

状态：实现、本地及指定提交的双平台原生交付检查已通过。P9.1 删除返回契约、旧 P3 总体回退与 P9.2 总体验收仍未完成。

## 问题和实现边界

在 f0f9725 已去掉同步 Upsert 共享票据槽之后，预热后的每次原子整数写入仍分配 8 字节键编码和 16 字节结果预算控制块。本次仅修改 SessionRuntime 的名额管理：将弱引用列表改为拥有控制块的有界池，强引用数等于一时才能复用。强引用数大于一说明请求、票据或完成端仍占用名额；控制块不保存用户输出、键值、请求、存储实例或请求身份。

Ticket/Completer 的字段、完成/收取逻辑和析构顺序不变。未收取的结果、仍存活的完成端继续占用容量；丢票据不取消任务。RequestId、generation、I/O 路由与版本登记保持独立，复用名额不会复用旧请求身份。所有操作仍在接受序号前预留名额，拒绝不消费序号。

池保留历史峰值数量的控制块直到 SessionRuntime 析构，正常配置下不超过 max_results。该容量保留只包含控制块及向量元数据，不保留用户数据。顺序请求优先复用最早的空闲项，无需每次扫描全部历史峰值；若内部调用传入更小的限额，则重新检查活跃名额总数，空闲槽不能绕过新限制，零限额始终拒绝。

没有新增依赖、生产 unsafe、公开 API 或文件格式变化。本实验中的 cfg(test) 模块在计时补丁中位于文件中部；正式源文件移到末尾以通过 Clippy，运行算法相同。

## 固定分配诊断

基线是 f0f97250f709e79563060c2b58d06e171be7702b；候选为同一提交加归档补丁。两端均为 Rust 1.98.1、全部特性、release、Null 设备，在同一 Apple M1 Pro / macOS 26.5.2 / APFS 上执行同一驱动。环境与工具链原始结果另行归档。

预热 128 次后统计 200,000 次同步原子热点写入：基线 400,000 次分配和释放、4,800,000 字节；候选 200,000 次分配和释放、1,600,000 字节。每次请求减少一笔 16 字节控制块分配，剩余 8 字节键编码。这里统计累计分配事件和请求字节，不能当作 RSS 或存活内存；计数探针的时间不作为吞吐测量。

## 完整短样本与异常保留

仍使用同一 200,000 次操作驱动，覆盖原子整数/变长值、256 键均匀/共享单键热点、1/4 线程。每个进程各三轮，按 AB/BA/BA/AB 顺序测量，每端每组完整保留 12 个样本。未并行运行构建、测试或其他性能进程。每次成功结果均检查输入序号，只重试接受前 Busy。

| 布局 / 分布 / 线程 | 吞吐比（候选/基线） | P99 比 |
| --- | ---: | ---: |
| 原子u64 / 256键均匀 / 1 | 1.135 | 0.834 |
| 原子u64 / 256键均匀 / 4 | 1.041 | 0.934 |
| 原子u64 / 单键热点 / 1 | 1.164 | 0.834 |
| 原子u64 / 单键热点 / 4 | 1.070 | 0.675 |
| 变长32至512字节 / 256键均匀 / 1 | 1.117 | 0.876 |
| 变长32至512字节 / 256键均匀 / 4 | 1.039 | 0.942 |
| 变长32至512字节 / 单键热点 / 1 | 1.067 | 0.963 |
| 变长32至512字节 / 单键热点 / 4 | 0.967 | 1.424 |

七组吞吐增加，但变长四线程热点 P99 比为 1.424，触发原有“吞吐下降超过 25% 或 P99 上升超过 30%”复核线。没有删除这个结果，也没有修改阈值。它促使下面的定向校准和更长采样；不能仅凭七组收益宣布全负载性能改善。

## 定向校准与长采样

定向驱动仅选择同一变长值、共享热点、四线程场景，其余请求构造、计时区间和校验逻辑不变。每种操作量先执行同一基线二进制的 A/A 校准，再独立执行基线/候选 A/B；各自采用 AB/BA/BA/AB 顺序，每端保留 12 个样本。A/A 中名为 candidate 的输出也实际运行 baseline 二进制。

| 单轮操作数 | 比较 | 吞吐比 | P99 比 |
| ---: | --- | ---: | ---: |
| 200,000 | 同二进制 A/A | 0.947 | 1.359 |
| 200,000 | 基线/候选 A/B | 0.963 | 0.944 |
| 2,000,000 | 同二进制 A/A | 1.066 | 0.985 |
| 2,000,000 | 基线/候选 A/B | 1.026 | 0.962 |

短样本的同二进制校准本身触发尾延迟复核，说明此场景存在显著运行波动，不能把最初 42% 全部归因于代码变化。延长单轮到 2,000,000 次后，校准与实际对照均未触发原线；候选观察到的吞吐增加约 2.6%、P99 下降约 3.8%，只作为本轮结果，不承诺稳定收益或公平性。

完整矩阵、短定向和长定向分别报告，没有混合样本来冲淡最初异常。三组实验合计 288 行、144,000,000 次真实业务操作，全部结果校验通过。该复核解释了本次热点异常；旧 P3 总体回退仍需单独处理。

## 契约与可复现证据

三个新增契约用例在修改前后均通过，覆盖：完成端/票据两种释放顺序，旧票据不能影响后续名额；丢弃票据后完成端继续占用容量；历史峰值有空闲槽时仍遵守降低后的限额及零限额。既有 F39/F40 继续覆盖真实 Pending、拒绝归还原请求、持有多个已取结果、关闭后结果存活及唯一析构。

[归档清单](data/p9-result-pool-experiment/manifest.json)包括全部 40 份原始计时 CSV、各组比较、分配诊断、三个驱动、执行脚本、基线/候选二进制哈希、环境和零上下文补丁。补丁可在固定 f0f9725 检出上用 git apply --unidiff-zero 回放，已实际重建源文件并比对。驱动和探针是独立诊断输入，不新增库的运行入口。

复核归档：

```sh
python3 tools/acceptance/audit_result_pool.py docs/acceptance/data/p9-result-pool-experiment
```

该命令核对哈希、唯一场景、固定操作数、分位数、全部样本及重算中位数，并保留打印触发原线的组。命令成功表示证据自洽，不代表旧 P3 门槛通过。重跑时使用两个隔离检出，依次复制对应 driver.rs、focused-driver.rs 或 long-driver.rs 为 examples/memory_matrix.rs，并以 cargo build --locked --release --all-features --example memory_matrix 构建。定向运行设置 RASTER_PERF_BYTES_HOT=1 并清除 RASTER_PERF_HOT_ONLY；完整矩阵清除两者。三个脚本记录了每次二进制选择与顺序，二进制生成完成后才能计时。
