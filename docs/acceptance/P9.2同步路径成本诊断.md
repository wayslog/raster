# P9.2 同步路径成本诊断

状态：已取得受限工作量的成本归因证据，未关闭旧 P3 总体性能复核。基线为正式实现 2842ef8957a24193d276daf999a5e1df0efae6b3。下述移除协议的变体只存在于诊断补丁和本地隔离检出，不能作为可交付引擎或功能验收结果。

## 诊断范围

目的不是继续猜测小开销，而是区分请求准备中几类必要协议的成本。固定单线程、单个 u64 键、Null 设备和驻留原子值；先预热 1,000 次，再执行 20,000,000 次 Upsert。每次检查同步成功返回，最后用真实 Read 读回值，并检查接受序号、会话关闭和存储关闭。只允许这一受限配置，不运行 Pending、磁盘 I/O、检查点、扫描或并发。

在同一 macOS 26.5.2、Apple M1 Pro、APFS、Rust 1.98.1 上，分别构建八种组合：保留全部协议，或移除邮箱登记/注销、版本表登记/等待、活动请求计数中的一个或多个。没有修改日志记录、值布局、原地写入、接受序号的全局登记及最终数据读取。移除邮箱的变体甚至复用固定路由，因此不满足普通引擎身份协议；其速度不能作为生产收益。

各变体先运行 1,000,000 次冒烟并实际读回。七个诊断变体分别与完整协议基线按 AB/BA/AB 顺序各运行三个样本，共 42 个平稳计时循环。计时区间不逐操作读取时钟或保留延迟数组，所以与原 memory_matrix 的时间口径不同；这里没有 P99，不用于替换原 25%/30% 复核规则。未固定 CPU 亲和性，原生 CI 制品下载/审计可能在后台并行；构建、SUT 测试和其他性能进程均与计时分开。

## 配对结果

每一行都使用它自己的配对基线。仅“活动计数”指不采样时仍维护的在途数量，不代表删去全部统计模块。

| 诊断移除项 | 完整协议 ns/次 | 诊断变体 ns/次 | 减少 ns/次 | 吞吐比 |
| --- | ---: | ---: | ---: | ---: |
| 活动计数 | 287.00 | 285.92 | 1.08 | 1.004 |
| 版本表 | 284.27 | 251.49 | 32.77 | 1.130 |
| 版本表 + 活动计数 | 286.24 | 251.08 | 35.16 | 1.140 |
| 邮箱 | 284.31 | 231.86 | 52.45 | 1.226 |
| 邮箱 + 活动计数 | 284.42 | 225.66 | 58.76 | 1.260 |
| 邮箱 + 版本表 | 282.97 | 192.33 | 90.64 | 1.471 |
| 邮箱 + 版本表 + 活动计数 | 285.31 | 188.11 | 97.20 | 1.517 |

邮箱和版本表对这个同步路径有可测成本，活动计数本身在本机影响很小。组合收益不是逐项简单相加：删除整个入口也会改变编译器生成代码和寄存器安排，因此这些数字不是各函数精确自耗时。数据支持继续优化登记结构或避免无用工作，不支持取消请求身份、背压、版本屏障或统计保证。

同一受限驱动再与旧 P3 7f2f03b646e85b30c81f31405e3dc2325086da2a 成对运行，各三个样本。当前完整协议中位数为 288.51 ns/次，旧版为 86.74 ns/次，成本比 3.326。两种版本均实际读回最终值并关闭成功。这个补充对照仍表明差距存在；不能将其与不同配对行相减，伪装成完整的严格成本分解。

## 采样与下一处可验证假设

在预热完成后另行采样当前完整协议二进制和旧 P3，分别请求 3 秒和 1 秒调用栈采样，两个进程最终都完成 40,000,000 次写入及真实值检查。当前采样二进制开启 release debug=1 以获得行号；采样产生的计时单独保存，完全不参与上表。两种版本都能观察到分配/释放调用，不能把全部差距归因于“旧版没有分配”。

当前调用图能定位到 [find_mutable](https://github.com/wayslog/raster/blob/2842ef8957a24193d276daf999a5e1df0efae6b3/src/log/mod.rs#L302) → [frontiers](https://github.com/wayslog/raster/blob/2842ef8957a24193d276daf999a5e1df0efae6b3/src/log/mod.rs#L232) → [PagePool::tail](https://github.com/wayslog/raster/blob/2842ef8957a24193d276daf999a5e1df0efae6b3/src/log/page.rs#L170)。源码显示可变记录查找只读取 begin/read_only/head，却通过通用 frontiers 同时读取了 tail，并取得页分配器锁。这是下一项可验证的冗余工作；尚未将它改成新的生产查询，也未忽略锁中毒或截断竞争的行为边界。不能把父子栈的累计样本数相加当成独立 CPU 成本。

## 归档与复现

[清单](data/p9-cost-attribution/manifest.json)记录固定源码提交、全部变体、二进制和文件哈希、原始 CSV、原始采样、环境、驱动及实际执行脚本。三个 baseline.rs 文件是构建诊断补丁时的源码快照；生产实现继续使用正常源码。

```sh
python3 tools/acceptance/audit_cost_attribution.py docs/acceptance/data/p9-cost-attribution
```

审计重新检查八种唯一组合、8 次冒烟、42 个配对循环、6 个旧版循环和 2 次采样后完整值校验，并重算中位数。共记录 1,048,000,000 次测量区间内的驱动提交，另有各进程预热及收尾读取。采样 CSV 被单独处理，不能混入平稳计时。

复现应在全新隔离检出中使用固定 2842ef8，复制 driver.rs 为 examples/cost_attribution.rs，将脚本和三个源码快照放入脚本指定的 target/p9-cost-attribution；build.py 构建八种诊断二进制后恢复三个生产模块，run.py 依固定顺序测量。compare_old.py 需要以同一驱动另构建旧 P3，profile.py 另构建带行号的当前二进制。RASTER_COST_DIAGNOSTIC 必须显式设置为“仅单线程驻留内存”，不得把这些诊断构建用于普通存储操作。

这些证据解释了一部分同步开销，并定位了后续工作；它们不证明旧 P3 性能门槛、上游删除契约或第一期总体验收已经完成。


后续对上述 tail 查询的实际候选、完整成对样本和保持契约的检查见[可变记录边界查询](P9.2可变记录边界查询.md)。成本诊断本身不代替该实现的交付检查。
