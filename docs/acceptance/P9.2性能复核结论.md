# P9.2 性能复核结论

状态：**性能复核与处理记录完成，当前性能限制保留。P9.2 整体仍等待 P9.1；第一期未完成。** 复核对象为 dbe392884be723708a0e6bdc0011de83f493f917，后续证据提交只修改文档及审核工具。

## 按原规则作出的结论

[P3 基线](P3内存性能基线.md)在优化前规定：同机、同工具链、同输入与计时方式下，吞吐下降超过 25% 或 P99 增加超过 30% 时启动复核，增加样本并检查调度/资源因素，解释或修复后再验收。[计划地图第 8 节](../14-RasterKV第一期实现计划地图.md#8-第一期完成标准)要求解释并处理回退，没有规定第一期必须达到旧内存原型或 C++ 的固定吞吐比例。

本次完整八组仍全部触发原数值线，原测量程序按原规则返回 1。复核结论不是“性能已经恢复”，而是：回退已复现并经过二分、完整同配置比较、受限成本实验和协议反例检查；已处理额外分配、重复查询及真实许可争用错误；正式实现保留完整的接受、版本、挂起与恢复协议，将剩余吞吐和扩展性差距作为明确的第一期性能限制交付。当前实现不能承诺旧 P3 原型的吞吐和尾延迟。

这一结论满足原规则要求的复核和处理，不重新设定一条更低的合格线。它也不证明每一纳秒已经归因或当前实现达到最优。P9.1 的删除返回契约仍未确定，P9.2/P9.3 整体未据此标为完成。

## 完整的同机对照

固定旧 P3 为 7f2f03b646e85b30c81f31405e3dc2325086da2a，当前为 dbe3928。两端分别重新构建相同 200,000 次驱动，全部特性、release、Rust 1.98.1，机器为 Apple M1 Pro / 16 GiB / macOS 26.5.2 / APFS。Null 后端没有日志文件 I/O。按旧/新、新/旧、新/旧、旧/新顺序运行，每个进程三轮，每端每组 12 个样本，共 192 行；执行前固定分组、顺序和原复核线。

另外分别执行相同配置输出程序，确认 13 个共同默认项逐项相同，包括 1,024 个索引桶、32 MiB × 4 日志页、0.9 可变比例、缓存关闭、自动压缩关闭及原会话/结果预算。当前新增的恢复和扫描流程没有在这个工作量中执行，统计采样关闭；必要的运行期协议与在途计数仍存在。

原驱动计时包含屏障、初次分配、工作循环及会话关闭，逐次延迟包含接受前 Busy 重试；保留原输出校验与同步完成要求。这个旧驱动逐次核对回调输出标识，真实四操作内容和恢复后全键检查另由正式矩阵验证。未绑定 CPU 亲和性；计时过程中没有并行构建、SUT 测试或其他性能进程。

## 新增协议的成本与必要性

旧 P3 的 [Upsert](https://github.com/wayslog/raster/blob/7f2f03b646e85b30c81f31405e3dc2325086da2a/src/engine/upsert.rs)直接在内存仲裁内完成查找与更新；尚无完整容量等待、设备完成、检查点切分和有界票据流程。当前 [Upsert](https://github.com/wayslog/raster/blob/dbe392884be723708a0e6bdc0011de83f493f917/src/engine/upsert.rs)还执行阶段观察、结果预算、请求身份/邮箱登记、同键版本许可和拥有型挂起任务收尾。旧版也已有记录租约和分配，不能将这些现有机制错误地归为后续新增。

本次在当前固定提交重新构建八个受限诊断变体，正交保留/移除邮箱登记、版本登记和 Upsert 入口阶段观察。只允许单线程、单键 u64、Null 后端、驻留原地写，预热 1,000 次后执行 20,000,000 次写；最后通过真实 Read 检查值、接受序号，并关闭会话和存储。每个变体与完整协议分别采用 AB/BA/AB 三个配对样本；另有八次 1,000,000 次冒烟。

相同受限驱动再与旧 P3 各配对三次：当前完整协议为 274.47 ns/次，旧版为 85.87 ns/次，成本比 3.196。这个驱动不逐操作读时钟或存储延迟数组，口径不同于上面的原驱动，没有 P99，不能取代原复核。

三个真实协议测试又分别在正常实现与单项移除变体上执行：正常实现均通过，移除后都以 101 和明确断言失败结束，非编译失败或空过滤：

| 移除项 | 实际失败 | 对应必要契约 |
| --- | --- | --- |
| 邮箱登记 | 第三个请求在容量为 2 时没有返回 Busy | 接受前容量预留及请求身份隔离；既有错身份、迟到完成场景继续保留 |
| 版本登记 | 新版本在旧版本仍活跃时提前 ready | 同键旧版本全部终结后，新版本才可执行 |
| Upsert 阶段观察 | 应自动观察新版本的提交被 Busy 拒绝 | 提交与轮询自动观察切分，旧请求仍归属原上下文 |

这些变体故意破坏契约，只用于诊断，未进入主线。全部三个生产模块在实验结束后恢复。不能将仅在受限工作量下正确读回的快速变体作为 RasterKV 交付。

当前完成邮箱、版本表和协调注册表分别由 Mutex 保护；业务条带锁覆盖 Upsert 的准备和执行。增加的全局串行化点及更长的同键仲裁路径与四线程更多重试相符。这里是基于源码和观测的解释，没有将单线程纳秒外推为四线程精确等待时间；完整的并发成本拆分和更高扩展性属于后续优化范围。

## 证据与复现

本次归档的 [manifest](data/p9-performance-review/manifest.json)包含共同驱动、固定计划、二进制/文件哈希、192 行完整对照、56 个受限循环、三组正常/失败协议日志、配置与分配输出及实际环境。受限循环累计 968,000,000 次测量区间操作，另有预热及收尾读取；原驱动另有 38,400,000 次提交成功。分配计数与配置输出分别记录，不能混入计时。

```sh
python3 tools/acceptance/audit_performance_review.py docs/acceptance/data/p9-performance-review
```

审核器重算全部分组、中位数、原复核判定、真实最终值和三个协议失败。它成功只表示材料一致，并会明确打印八组仍触发原线。故意篡改中位数、原复核线或协议失败结论时，即使重算文件哈希也必须被拒绝。

复现原对照时，在固定两端检出复制 p3/driver.rs 为 examples/memory_matrix.rs，按 p3/plan.json 顺序运行全部特性 release；cost/ 脚本需要自有隔离检出，按记录的八个补丁构建，每次只改变明确的协议项。计时与编译、分配计数、协议失败测试分开运行；诊断完恢复源码。全部脚本使用 target 下明确的实验目录，复现时按自己的检出布局安排。

当前正式实现 dbe3928 的 13 个原生任务、双平台各 48 组四操作/恢复矩阵、每平台 72 次资源生命周期和 144 次恢复均已通过，见[原生交付表](P9.2可变记录边界查询.md#指定提交的原生交付)。其报告提交 76a67e4 的 11 个自动任务也完成并经制品审计。P9.1 的 A02/A05 删除返回选择，以及 P9.3 的第一期最终文档快照仍待完成。
