# C++ 性能持平调研与执行记录

## 目标和验收范围

目标是保持第一期已经交付的功能与行为契约，使 RasterKV 与固定 C++ FASTER 上游在相同工作负载下基本持平。上游固定为 `321d872eabda6a0345c8bd76419f89723ed864ae`。既有 P9 文档比较当前 Rust 与早期 Rust 原型；其比值不能作为 C++ 性能差距的证据。

本轮在取得新测量之前固定判据：Rust 吞吐量至少为 C++ 的 90%，P99 至多为 C++ 的 110%。使用同机交替进程样本，保留原始输出、工具链、源提交、二进制哈希和校验结果。不能以放宽判据、缩小功能范围或删除安全协议宣称完成。

完整目标仍须覆盖整数与变长值、四操作、单线程与多线程、均匀与热点、内存与超内存，以及检查点、恢复、扫描、压缩和自动维护；第一组内存微基准仅用于缩小故障范围，不代表整体交付验收。

## 直接引擎微基准 v1

- Rust 入口：`examples/parity.rs`；C++ 入口：`tools/performance/memory.cc`。
- C++ 使用未修改的固定上游核心。两端直接调用 API，不使用行为对照器的逐操作消息队列、promise/future 和文本格式化。
- 两端均使用 8 字节整数键、相同的小端 FNV-1a 哈希、8 字节原子整数值、1024 个索引桶、256 MiB 日志内存、32 MiB 页、0.9 可变比例、空设备。读缓存、统计和自动压缩关闭。上游要求至少 6 页，RasterKV 默认的 4 页不能直接用作公共配置，因此两端显式配置为 8 页。
- 预装每线程 256 个键，值为 7。覆盖写固定为 42，RMW 每次加 1。均匀分布使用线程独立键区和步长 17；线程热点使用各自第一个键；共享热点使用键 0。
- 每次运行一个场景。线程创建、建库、预装、关闭、最终验证和 JSON 输出不计入业务时间。吞吐量使用操作总数除以最慢工作线程的业务时长。
- 每 256 次操作刷新一次会话。Rust 拒绝的 Busy 用相同序号重试；接受的 Pending 驱动原 ticket 完成，禁止重提。相关成本包含在计时内，并记录计数。
- 每 64 次操作采样一次延迟，采样位置逐块轮换。每端先运行一次不参与统计的预热进程，随后默认四轮 AB/BA 顺序交替，每轮 200 万操作。
- 驱动验证全部最终值。独立 Python 模型另行验证最终摘要、操作输出总和、操作数、线程数和验证键数；因此两端输出相同也不能绕过参考模型。
- 初始范围是读、覆盖写、RMW × 三种分布 × 1/4 线程，共 18 组。删除、变长值与持久化生命周期必须后续补齐。

原生 Linux 构建和运行：

```sh
cargo build --locked --release --example parity
sh tools/performance/build.sh target/upstream-source target/parity-build
python3 tools/performance/compare.py \
  --rust target/release/examples/parity \
  --cpp target/parity-build/faster-memory \
  --output target/parity-evidence/memory
```

`--case upsert/uniform/1` 可缩小为单个场景。输出目录必须是新目录；未达到性能判据时返回非零状态并保留原始结果。GitHub `benchmark.yml` 的 `cpp-parity` 模式在原生 Ubuntu 24.04 执行同一循环。本地 macOS ARM 的 Rust 单端结果仅用于校验驱动和定位，不与 x86 模拟运行结果组合为持平证据。

### 剩余的主要结构成本

在 `951ba14` 关闭缓存、统计与自动维护，且命中可变内存记录的 Upsert 路径上，静态调用链至少包含以下 12 次 Mutex 获取，以及一次索引路由读锁。数字表示获取次数，不等同于发生操作系统休眠的次数，也不能直接换算成固定耗时。

| 位置 | Mutex 获取次数 | 当前职责 |
| --- | --- | --- |
| Epoch 进入与退出 | 2 | 访问保护与安全回收 |
| 协调器观察与序号接受 | 2 | 阶段切换、身份与单调序号 |
| 按哈希分组的操作仲裁 | 1 | 业务操作间仲裁 |
| 完成邮箱保留与释放 | 2 | 路由容量、身份与迟到完成 |
| 版本许可登记、就绪检查、退出 | 3 | 同键跨版本顺序 |
| 日志可变边界与记录表查找 | 2 | 边界检查与记录存活 |

固定上游 `faster.h` 的 `InternalUpsert` 在 `REST` 阶段直接取得线程执行上下文，只有非 `REST` 才进入 `HeavyEnter`；内存命中通过 `hlog.Get(address)` 取得记录。RasterKV 当前还在每个常态操作中执行上述共享控制和记录表查找，因此只调整容器不足以达到目标。

后续优先建立带并发测试的常态路径：明确哪些状态由会话独占，哪些登记仅在 Pending 或版本切换时需要，以及何时可以发布检查点分界。任何延迟登记都必须证明 Prepare/InProgress/WaitPending、拒绝不消费序号、旧版本排空、会话关闭及最后读者退出的行为不变；不能直接删除这些协议来获得吞吐量。短键的拥有型编码复用、日志地址解析也需要单独测量。

以上都是局部收益，不能视为与 C++ 持平。后续继续减少请求登记、版本观察及日志查找中的共享控制成本，并补齐删除、变长值和持久化生命周期对比。

### 第三处候选：版本就绪状态缓存与登记分片

只要一个版本许可仍在登记表内，比它更旧的新登记就会被拒绝。因此，一旦已有旧版本全部退出，该许可的就绪状态不会回退，可以缓存首次肯定结果。缓存使用 release/acquire 发布已完成旧请求的顺序；任何登记表中毒仍会拒绝执行。每次正常同步操作由三次版本锁获取降为两次。

其次按完整哈希分为 64 个独立登记表，同一完整哈希始终进入同一分片；分片碰撞仍按完整哈希和版本区分。分片分别对齐缓存行，任一分片在持锁期间发生 panic 仍会使整个登记器失败关闭。沿用 std Mutex 自身的中毒判断，避免把已存在的用户 unwind 误判为新中毒。

六项专门测试覆盖旧版本排空、就绪单调性、旧版本重新插入拒绝、分片碰撞、整体中毒及既有 unwind 清理；本地全特性单元、集成和 doctest 共 452 项通过，0 失败、0 忽略，全目标 Clippy 通过。

本地四轮交替样本中，单独缓存就绪状态使单线程均匀 Upsert 吞吐比为 1.025，四线程独立热点 RMW 为 1.219。分片在此基础上继续提高四线程 RMW 吞吐，但单线程及共享热点的 P99 样本不稳定，不能据此宣布分片已验收。初版重复检测 panic 状态的包装已替换为 Mutex 中毒通知。原始样本、中间源码及补丁见 [本地实验归档](data/cpp-parity-version-local.tar.gz) 与 [清单](data/cpp-parity-version-local.json)。

比较工具新增 `--baseline-rust`，继续使用同一输入及独立结果模型。GitHub `cpp-parity` 工作流可通过 `baseline_ref` 指定完整旧提交，在同一 runner 构建并交替运行旧、新 Rust；即使 C++ 持平门槛失败也会执行这项对照。Rust 自身回归门槛为吞吐比至少 0.98、P99 至多 1.10；C++ 的最终 0.90/1.10 门槛保持不变。

`321bc04` 的 [原生 Linux 同机对照](https://github.com/wayslog/raster/actions/runs/34685574411) 已完成：与 `24c20d1` 比较，四线程均匀及独立热点的六组吞吐比为 1.688–1.710，P99 比为 0.241–0.282；单线程九组吞吐比为 1.013–1.049。17/18 组通过自身回归门槛，四线程共享热点 Upsert 的吞吐比为 1.073、P99 比为 1.136，后者仍不合格。其四轮样本均无 Pending，拒绝重试约 275–286 万次，旧版为 297–313 万次；不能把吞吐收益解释为尾延迟也已改善。

### 第四处候选：借用已持有的 Engine

Session 在四操作和 poll 的整个调用期间均拥有 Engine；Upsert、RMW、Delete 任务也在 advance 期间持有 Engine。原先八处局部 Arc 克隆仅为借用这些字段，每次增加和减少同一个共享引用计数。改为字段借用后，Pending 任务仍独立拥有 Engine，Epoch guard 的存活范围不变。

### 已撤回的第五处候选：REST 版本观察

协调器在未执行维护动作时用原子值发布 REST 版本；动作启动在更改状态前使该值失效，只有正常结束才重新发布。Session 版本与此值一致时，observe_session 可省去一次全局登记锁读取。登记锁中毒及 u64::MAX 版本始终回退到原观察路径。所有原子访问使用 SeqCst，缓存不与频繁修改的登记锁共享缓存行。

该值只替代瞬时状态观察，不是跨操作许可。观察结束后动作仍可启动，原序号接受继续在登记锁下检查身份、版本和严格递增；会话的 Prepare/InProgress/WaitPending 屏障、固定旧分界和 Epoch 范围保留。新增测试覆盖观察后由另一线程启动检查点、旧版本拒绝不消费序号、正常发布、恢复初始化、失败、中毒及版本耗尽。

### 第六处候选：短键编码内联存储

四操作准备规范键编码时，16 字节以内直接使用拥有型内联缓冲，更长的编码仍使用可失败分配的 Vec。读/RMW 查询复制短键也不再分配。所有编码器仍取得原长度的零初始化输出切片；哈希、编码算法、回调次数、磁盘格式和 Pending 的拥有型生命周期不变。没有引入 unsafe、依赖或公开 API。

### 第七处候选：稳定 Epoch 槽位与有限的接受前重试

新增的实际接口测试在旧实现上失败：持有全局登记表检查锁时，已登记参与者无法进入。候选让 Session 持有稳定槽位句柄，每次进入/退出只借用句柄并修改所属槽位；全局登记锁继续排序注册、注销、epoch 推进和延迟动作收集。槽位锁不跨业务回调持有，嵌套访问保留最早 epoch，复用验证代次，控制表或任一槽位中毒都使整体失败关闭。收集的安全条件和锁顺序已同步到 [状态协议](../11-RasterKV内存与状态协议.md)。

12 项 Epoch 测试通过，覆盖 210 种完整接口交错、真实并发的新旧读者分批退出、稳定句柄跨登记表扩容、同槽嵌套、身份隔离、代次/计数/epoch 耗尽、中毒和已存在的 unwind 清理。没有引入 unsafe 或新的依赖；这仍是按参与者加锁的实现，不是无锁 Epoch。
