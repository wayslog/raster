# C++ 性能持平调研与执行记录

## 目标和验收范围

目标是保持第一期已经交付的功能与行为契约，使 RasterKV 与固定 C++ FASTER 上游在相同工作负载下基本持平。上游固定为 `321d872eabda6a0345c8bd76419f89723ed864ae`。既有 P9 文档比较当前 Rust 与早期 Rust 原型；其比值不能作为 C++ 性能差距的证据。

本轮在取得新测量之前固定判据：Rust 吞吐量至少为 C++ 的 90%，P99 至多为 C++ 的 110%。使用同机交替进程样本，保留原始输出、工具链、源提交、二进制哈希和校验结果。不能以放宽判据、缩小功能范围或删除安全协议宣称完成。

完整目标仍须覆盖整数与变长值、四操作、单线程与多线程、均匀与热点、内存与超内存，以及检查点、恢复、扫描、压缩和自动维护；第一组内存微基准仅用于缩小故障范围，不代表整体交付验收。

## 直接引擎微基准 v1

- Rust 入口：`examples/parity.rs`；C++ 入口：`tools/performance/memory.cc`。
- C++ 使用未修改的固定上游核心。两端直接调用 API，不使用行为对照器的逐操作消息队列、promise/future 和文本格式化。
- 两端均使用 8 字节整数键、相同的小端 FNV-1a 哈希、8 字节原子整数值、1024 个索引桶、256 MiB 日志内存、32 MiB 页、0.9 可变比例、空设备。读缓存、统计和自动压缩关闭。上游要求至少 6 页，RasterKV 默认的 4 页不能直接用作公共配置，因此两端显式配置为 8 页。
- 预装每线程 256 个键，值为 7。覆盖写固定为 42，RMW 每次加 1。均匀分布使用线程独立键区和步长 17；线程热点使用各自第一个键；共享热点使用键 0。
- 每次运行一个场景。线程创建、建库、预装、关闭、最终验证和 JSON 输出不计入业务时间。吞吐量使用操作总数除以最慢工作线程的业务时长。
- 每 256 次操作刷新一次会话。Rust 拒绝的 Busy 用相同序号重试；接受的 Pending 驱动原 ticket 完成，禁止重提。相关成本包含在计时内，并记录计数。
- 每 64 次操作采样一次延迟，采样位置逐块轮换。每端先运行一次不参与统计的预热进程，随后默认四轮 AB/BA 顺序交替，每轮 200 万操作。
- 驱动验证全部最终值。独立 Python 模型另行验证最终摘要、操作输出总和、操作数、线程数和验证键数；因此两端输出相同也不能绕过参考模型。
- 初始范围是读、覆盖写、RMW × 三种分布 × 1/4 线程，共 18 组。删除、变长值与持久化生命周期必须后续补齐。

原生 Linux 构建和运行：

```sh
cargo build --locked --release --example parity
sh tools/performance/build.sh target/upstream-source target/parity-build
python3 tools/performance/compare.py \
  --rust target/release/examples/parity \
  --cpp target/parity-build/faster-memory \
  --output target/parity-evidence/memory
```

`--case upsert/uniform/1` 可缩小为单个场景。输出目录必须是新目录；未达到性能判据时返回非零状态并保留原始结果。GitHub `benchmark.yml` 的 `cpp-parity` 模式在原生 Ubuntu 24.04 执行同一循环。本地 macOS ARM 的 Rust 单端结果仅用于校验驱动和定位，不与 x86 模拟运行结果组合为持平证据。

### 诊断与首个候选修改

macOS ARM 原生单线程覆盖写的 5 秒采样中，工作线程有 3728 个样本：日志 lease 查找、邮箱有序树插入/删除、控制锁、版本范围查询均在热路径；没有证据支持哈希是主要原因。此采样用于定位，不与 Linux C++ 数字直接比较。

首先试验了标准 HashMap 替换邮箱有序表。与固定 Rust 基线的同机四轮交替样本比较，覆盖写单线程吞吐仅提高 1.5%，四线程热点 P99 上升 18.5%，因此弃用。

随后改为复用 4 个固定邮箱槽，超过 4 个在途请求时使用原有 BTreeMap。所有槽仍受原控制锁保护；全局容量、单调路由号、请求身份校验、迟到完成丢弃和一次终结契约保留。增加覆盖固定槽复用、有序表溢出、迟到完成与容量拒绝同时出现的测试。

候选修改的 macOS 同机四轮交替样本结果如下。每端各有一次不计入统计的预热，每轮 200 万操作，所有输出与独立模型一致。

| 场景 | 候选吞吐 / 原 Rust | 候选 P99 / 原 Rust |
| --- | --- | --- |
| 单线程均匀 Upsert | 1.168 | 0.899 |
| 单线程均匀 Read | 1.130 | 0.846 |
| 四线程独立热点 Upsert | 1.035 | 0.953 |

原始本地逐轮数据及二进制/源码哈希见 [邮箱候选测量](data/cpp-parity-mailbox-local.json)，路径脱敏后的原始采样见 [采样归档](data/cpp-parity-upsert.sample.txt.gz)。本地 `cargo test --locked --all-features` 共 445 项通过、0 失败、0 忽略，包含单元、集成及 doctest；格式检查、全目标全特性 Clippy 和文档/历史归档检查通过。

这是局部收益，不能视为与 C++ 持平。下一步仍须在原生 Linux 确认候选结果，继续减少请求登记、版本观察及日志查找中的共享控制成本，并补齐删除、变长值和持久化生命周期对比。
