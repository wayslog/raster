## 二、构建产物与依赖组织

### 2.1 主体是模板头文件加小型静态库

`cc/src/CMakeLists.txt:57–73` 只编译四个 `.cc`：

- `core/address.cc`。
- `core/lss_allocator.cc`。
- `core/thread.cc`。
- MSVC 下的 `environment/file_windows.cc`，或其余编译器下的 `environment/file_linux.cc`。

产物为静态库 `faster`。`FasterKv`、`F2Kv`、索引、设备和大部分算法在头文件中，调用方实例化模板。因此 Rust 改写的工作量集中在模板实现与跨组件契约，不能根据静态库源文件数量估算。

当前 CMake 没有 `install()`、导出 package 或稳定 C ABI 声明；使用入口是 C++ 头文件、模板实例化、静态库及系统库链接。`cc/CMakeLists.txt:63` 使用 `${CMAKE_SOURCE_DIR}/src`，表明其默认假设 CMake 源根为 `cc/`；直接作为另一顶层工程子目录嵌入需要核查路径。

### 2.2 构建配置

| 项目 | 当前行为 | 源码 |
|---|---|---|
| CMake 最低版本 | 3.14 | `cc/CMakeLists.txt:1` |
| 非 MSVC 语言模式 | `-std=c++17` | `cc/CMakeLists.txt:26–30` |
| MSVC 语言模式 | `/std:c++20` | `cc/CMakeLists.txt:17–22` |
| Debug | 非 MSVC `-O0 -g -D_DEBUG -DTOML_CONFIG` | `cc/CMakeLists.txt:29` |
| Release | 非 MSVC `-O3 -g -DTOML_CONFIG` | `cc/CMakeLists.txt:30` |
| `USE_URING` | 默认 OFF；非 MSVC Debug/Release 增加 `FASTER_URING`，链接 `uring`，增加对应测试 | `cc/CMakeLists.txt:15,32–35,80–82` |
| `USE_BLOBS` | 默认 OFF；增加 Azure 库链接和 blob 测试目录 | `cc/CMakeLists.txt:14,84–86,123–126` |
| 产物位置 | archive/library/runtime 统一到构建目录 | `cc/CMakeLists.txt:65–68` |
| 测试注册 | 每个目标一个 CTest 测试，内部使用 GoogleTest | `cc/CMakeLists.txt:100–107` |

`TOML_CONFIG` 和 `FASTER_URING` 在非 MSVC 分支只写入 Debug/Release flags。使用空 `CMAKE_BUILD_TYPE`、`RelWithDebInfo` 等配置时，不能直接假定宏行为与 Release 相同。项目也没有显式的“仅库、不构建测试与基准”开关：四个主要子目录始终加入，GoogleTest 始终获取。可以只构建 `faster` target，但配置阶段仍包含这些依赖。

`cc/CMakeLists.txt.in` 里的 GoogleTest `main` 下载模板不是当前实际依赖版本入口；实际入口使用 `FetchContent`。

| 依赖 | 获取或链接方式 | 用途/边界 |

### 2.4 平台边界

源码显式提供 Windows 和 Linux 两套文件实现（`cc/src/environment/file.h:6–10`）；Linux 实现直接包含 `<libaio.h>`，可选包含 `<liburing.h>`（`file_linux.h:9–15`）。非 Windows 分支不是通用 POSIX 实现。当前工作环境为 macOS，不能把“CMake 存在”当成原仓库已支持 macOS；本文没有尝试本机编译。

编译源选择以 `MSVC` 为条件，部分链接及头文件选择以 `WIN32`/`_WIN32` 为条件；例如 MinGW 不应直接视为已经验证的 Windows 组合。Rust 迁移应显式确定第一阶段平台及设备后端范围。

## 三、可复用的构建和检查入口

以下命令是依据当前 CMake 得出的执行入口，尚未执行。建议在 Linux 环境使用独立构建目录：

```sh
cmake -S FASTER/cc -B /tmp/faster-cpp-debug -DCMAKE_BUILD_TYPE=Debug
cmake --build /tmp/faster-cpp-debug --parallel
ctest --test-dir /tmp/faster-cpp-debug --output-on-failure
```

Linux 上应把示例中的 macOS 源路径替换为实际检出路径。只列测试可使用 `ctest --test-dir <构建目录> -N`；单独检查内存实现使用 `ctest --test-dir <构建目录> -R in_memory --output-on-failure`。启用 io_uring 时配置增加 `-DUSE_URING=ON`，启用 Azure 路径增加 `-DUSE_BLOBS=ON` 并预先满足外部服务及依赖条件。

Windows 仓库使用 `Visual Studio 17 2022` 生成器，构建后使用 `ctest -C Debug` 或 `-C Release`；实际 CI 命令见 `azure-pipelines.yml:92–103`。

## 五、示例、辅助工具及其输入输出

| 可执行目标 | 输入与行为 | 输出/副作用 | 源码 |
|---|---|---|---|
| `sum_store` | `single populate`、`single recover <token>`；`concurrent <线程数> populate/recover/continue [token]` | `sum_storage` 目录，执行写入、检查点、恢复或续跑示例；构造 16 GiB 日志配置 | `cc/playground/sum_store-dir/sum_store.cc:13–69` |
| `read_log_metadata` | 一个日志元数据文件路径 | 标准输出打印 snapshot 标志、版本、线程数、flush/final 地址、serial number、GUID | `cc/playground/recovery-info/read_log_metadata.cc:11–48` |
| `read_index_metadata` | 一个索引元数据文件路径 | 标准输出打印表大小、索引/溢出桶字节数、桶尾及日志地址 | `cc/playground/recovery-info/read_index_metadata.cc:11–39` |
| `process_ycsb` | 原始 YCSB basic 文本、目标文件路径 | 从 `usertable user` 后提取整数，逐个写入本机表示的 `uint64_t` 原始字节 | `cc/benchmark-dir/process_ycsb.cc:12–38` |

`sum_store` 的帮助文本声称 `single` 有 `continue`，但实际 `single` 分支只处理 `populate` 与 `recover`；`continue` 仅在 `concurrent` 分支实现。Rust CLI 契约应按实现确认，而非直接复制帮助文本。

两个 metadata 工具按 `sizeof(IndexMetadata/LogMetadata)` 直接读取并 `reinterpret_cast` 原生结构；它们是调试工具，不能视为独立、可移植的文件格式解析规范。当前还存在 `fread(buffer, size, 1, f)` 返回“元素数”却和 `size` 比较、未检查 `fopen` 空指针的问题（两文件 `:21–25`）。移植时应重建验证明确的解析接口。

## 六、性能基准入口

- `benchmark <workload> <线程数> <load文件> <run文件>`：实例化 FasterKv，日志内存配置 16 GiB，路径 `storage`（`cc/benchmark-dir/benchmark.cc:14–34`）。
- `benchmark_f2` 参数相同：内存热索引加 ColdIndex，实际构造热日志 **4 GiB**、冷日志 **12 GiB**，路径 `storage-f2/hot_` 和 `storage-f2/cold_`（`benchmark_f2.cc:16–19,38–48`）。同文件上方注释写的是 6/10 GiB，调查以构造参数为准。
- workload 枚举为 `0=A_50_50`、`1=RMW_100`、`2=B_95_5`、`3=C_100_0`（`benchmark.h:30–35`）。README 只展示前两种。
- 默认按时间运行：30 秒；加载 2.5 亿键，事务键数组 10 亿项；刷新间隔 64，CompletePending 间隔 1600（`benchmark.h:42–59`）。不是适合直接在开发机试跑的小示例。
- 输出包括每线程读写次数、耗时，以及 `ops/second/thread` 和完成检查点计数（`benchmark.h:572,658`）。不能把每线程指标误报为全局吞吐。
- `process_ycsb` 输出是原始 8 字节整数序列，不是换行分隔的十进制文本；README 的整数示意不应直接作为实际加载格式。

## 七、对 Rust 改写组织的直接建议

1. 将 `core/index/device/environment` 四层映射为清晰模块边界，并独立保存测试及基准；不要按现有少量 `.cc` 划分工作量。
2. 首先建立“纯内存 + Linux 本地磁盘”可执行基线，之后再决定 F2、io_uring、Windows、Azure 各自的兼容目标；这是分阶段建议，不是删减原始功能清单。
3. 将分页和恢复共享测试改为针对设备接口的同一套 Rust 行为测试，保留并发、可变长、重插入、读压缩竞态等关键维度。
4. 从小数据集基准开始对齐操作语义与完成条件，再运行原始规模；现有硬编码超大数组和日志参数需要显式配置化。
5. 若要求读取 C++ 既有持久化文件，单独建立字节布局与恢复兼容验证；当前 metadata 工具和原生结构读取方式不足以保证 Rust 兼容。
